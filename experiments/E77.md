## E77 PRE-REGISTRATION - does KV precision change ANSWERS? (2026-08-28)

**Registered BEFORE any bank item has been run.** Gate 0 - the serving spike -
is complete and its measurements are declared below, because they changed the
design and it would be dishonest to present the amended design as the original
one. No item from either bank has been run and no answer has been read.

First experiment of the inference-architecture programme. Scope, and the
reconciliation of the plan's 24 hypotheses against E1-E76:
`docs/plans/2026-08-28-inference-architecture-slice-1.md`.

### Why this experiment exists

| | |
|---|---|
| **which success question** | the reliability half. F16 recommends q8_0 KV for long-context work on **throughput** evidence and this repository has never measured whether it changes an answer |
| **uncertainty reduced** | whether KV precision is a free lever on this hardware, or a quality trade dressed as a memory saving |
| **decision that changes** | the relay serves `-c 98304` with **no `-ctk`/`-ctv` flag at all**, so production runs an F16 KV cache while our own findings register recommends otherwise. Either the recommendation ships or it gains a caveat |

It is also the plan's **B0**: the f16 control arm re-anchors the KA-H1 bank on
kernel `7.0.0-29-generic` with full run metadata, extending E76's 9-of-9 control
bridge to all 24 items.

### GATE 0 - the serving spike, run 2026-08-28, before registration

Four servers, one KV type each, frozen build 770 (`9e40df63b`), Vulkan/RADV.
**The flag was not trusted from the command line - it was proved from the
startup line and then again from GTT**, because four arms returning
byte-identical answers to a 28-token prompt is also exactly what a flag that
does nothing looks like.

**Qwen3-30B-A3B-Instruct-2507-Q4_K_M at `-c 32768`, 48 layers, no recurrent
state, zero filtered layers - every layer's KV is quantised:**

| `-ctk`/`-ctv` | reported KV size | K | V | GTT delta | loads |
|---|---|---|---|---|---|
| `f16` | 3072.00 MiB | 1536.00 | 1536.00 | **20.318 GiB** | yes |
| `q8_0` | 1632.00 MiB | 816.00 | 816.00 | 18.912 GiB | yes |
| `q5_1` | 1152.00 MiB | 576.00 | 576.00 | 18.428 GiB | yes |
| `q4_0` | 864.00 MiB | 432.00 | 432.00 | 18.162 GiB | yes |

Weights are 17,524.42 MiB and constant, so the GTT differences are the KV
differences and they reconcile against the server's own figures: f16 - q8_0 is
**1.406 GiB measured against 1440 MiB reported**, and f16 - q4_0 is **2.156 GiB
against 2208 MiB** - both exact. f16 - q5_1 is 1.890 GiB against 1920 MiB
reported, **15.7 MiB over**, which is the shared GTT counter moving under a live
relay rather than an allocation difference. Stated rather than rounded away.

**Two findings from the spike that change the design:**

1. **Quantised V forces flash attention on.** Every quantised arm logs
   `enabling flash_attn since it is required for quantized V cache`, while the
   f16 arm runs `flash_attn = auto`. That is a second variable. The f16 log then
   shows `resolve_fused_ops: Flash Attention enabled`, so `auto` does resolve on
   for this model - but **every arm is registered with `-fa on` explicitly**
   rather than depending on `auto` resolving the same way at a different `-c` or
   on a different model. Rule 8: name the config a finding needs.

2. **Qwen3.8-27B is a hybrid and `-ctk`/`-ctv` reaches a quarter of it.** It has
   `n_layer = 64` (`n_layer_all` 65, `qwen35.block_count` 65) and at `-c 32768`
   its KV cache covers **16 of those 64 layers**. The other 48 are Gated DeltaNet,
   logged as `filtered`, and their state lives in a **149.62 MiB recurrent-state
   buffer that is byte-identical across f16, q8_0 and q4_0**. KV quantisation does
   not touch it. The workhorse, by contrast, is `n_layer = 48` with **zero filtered
   layers and no recurrent state at all**.

   **This property was already banked and I am not claiming it as new.** E44's
   registration records the same split - *"KV for only 16 of 64 layers (2,048 MiB
   at 32,768 cells = 64 KiB/token), the other 48 holding a constant 149.62 MiB
   recurrent state"* - measured for a memory-headroom check. The spike reproduces
   it independently, which is a useful agreement between two measurements taken
   ten days and one kernel apart. What is new is only the CONSEQUENCE: no
   experiment before this one varied KV precision, so nobody had reason to ask
   what a hybrid does to the instrument.

| Qwen3.8-27B `-c 32768` | KV size | recurrent state |
|---|---|---|
| `f16` | 2048.00 MiB (16 of 64 layers) | 149.62 MiB |
| `q8_0` | 1088.00 MiB | 149.62 MiB, unchanged |
| `q4_0` | 576.00 MiB | 149.62 MiB, unchanged |

**This demotes Qwen3.8 from primary to secondary**, and the registration below
says so before any answer exists. A null result on a hybrid would mean "KV
precision is harmless for the 16 attention layers of this architecture", which
is a materially weaker claim than the one the hypothesis makes.

### Primary metric

**`correct_to_wrong`** - items correct under f16 and wrong under the quantised
arm, scored per item by `tools/score_kw_eval.py` at `SCORER_VERSION` v2 and by
the L3 validator. **Not mean accuracy.** Two arms can both score 21/24 while
disagreeing on four items, and averaging hides exactly the failure this
experiment exists to find.

Secondary: `wrong_to_correct` (its honest counterpart - a quantised arm that
*gains* an item has told us the bank is noisy, not that compression helps),
`citation_valid`, `wrong_document` (instrument B), reported KV MiB, GTT delta,
prefill and decode rates.

## E77 RESULT - q8_0 KV changes what the model SAYS on nine items in ten and what it gets RIGHT on none. PREDICTIONS 3 AND 5 FALSIFIED. (2026-08-28)

Eleven arms. Instrument A ran 13:22-13:39, instrument B 13:41-14:13, kernel
`7.0.0-29-generic`, `canonical-livepatch` reporting `nothing-to-apply` before
and after with nothing moving in between. **Rule 9 breached as registered; every
wall time is VOID and none is quoted below.**

### THE ANSWER

> **On the production model, q8_0 and q5_1 KV change no verdict at either depth,
> and q4_0 costs one item of twenty-four. But q8_0 rewrites the ANSWER TEXT on
> nine items in ten.** Compression that is free on the score is not free on the
> output, and this repository had no way of knowing that until the noise floor
> was measured.

### Both controls came back clean, and one is stronger than it was registered to be

**Prediction 6, the kernel bridge: 24 of 24 per-item verdicts unchanged** against
the banked `7.0.0-28` workhorse run, where the prediction needed 22. The banked
21/24 reproduces exactly, 9/11 and 12/13 per pack.

**And the answers themselves are byte-identical on 24 of 24 items** - across a
kernel change, nine days, a different `llama-server` process and a runner that
gained `include_usage` in between. That was not registered as a control and is
the more useful of the two:

> **The noise floor for this model on this bank is ZERO.** So every text
> divergence in the tables above is attributable to the KV flag and to nothing
> else. Without this measurement the divergence column would have been
> uninterpretable, because run-to-run variation would have explained it equally

**Prediction 3 is falsified on the field it named and supported by a field it
did not.** Median answer similarity at q4_0 falls 0.771 on `s` to **0.470** on
`m`, so text fidelity does degrade with depth exactly as the reasoning behind
the prediction expected. The verdict metric did not see it. That is the E64 and
E32 lesson arriving a third time: **a prediction is scored against the field it
names**, and naming the coarser of two available fields costs you the result.

### The two q4_0 moves, named rather than netted to zero

Their sum is zero and reporting it that way would be false.

- **`K18` is a real loss.** The f16 answer gives the specific figure - *"up to
  **three questions in twenty** being answered incorrectly"* - and the q4_0
  answer, at twice the length, generalises to *"lost answers and increased
  computational cost"* and never states it. Losing the number is the failure
  mode professional document work cares about.
- **`K07` is a matcher artefact, not a gain.** Both arms say the same thing -
  use Qwen3.8-27B, do not use the workhorse, citing the routing guide - and
  q4_0's more explicit list formatting happened to satisfy the mechanical check
  where f16's prose did not. `wrong_to_correct` was registered precisely to
  expose this: **a quantised arm that gains an item has told us the bank is
  noisy, not that compression helps.**

### Why instrument B saw nothing, and why that corroborates its demotion

The hybrid moved **11 of 12 and 10 of 12 answers byte-identically** at q8_0 and
q4_0, median similarity **1.000**, against the dense model's 1-to-3 of 13. The
mechanism is the one Gate 0 measured: **only 16 of Qwen3.8's 64 layers hold a
quantisable KV cache**, and its 149.62 MiB recurrent state is untouched by any
arm. Three quarters of its state never sees the flag.

So instrument B's triple 12/12 is not evidence that KV precision is harmless.
It is evidence that **this instrument cannot see the variable**, which is what
the registered demotion said before any answer existed. The tie-break did not
need to fire - the instruments do not disagree - but the reasoning that produced
it is now measured rather than argued.

### The decision rule fires, and the honest bound comes with it

The registered branch: *q8_0 `correct_to_wrong` = 0 on instrument A, both packs
-> recommend q8_0 KV for the relay's long-context serving.* It fires.

**What the memory saving actually is, at the relay's own context.** KV is exactly
linear in cells - measured at two points, 3072 -> 6144 MiB for f16 and 1632 ->
3264 for q8_0 across a doubling - so at the production `-c 98304` this is
**9216 MiB against 4896 MiB, a saving of 4.219 GiB**. That is a projection from
two measured points and is labelled as one.

**And the bound this bank can support is not tight.** Zero flips in 24 items is
a 95% Wilson interval of **0.00% to 13.80%** on the true flip rate (one-sided
exact upper bound 11.73%), estimator `wilson-v2-2026-08-20`. Pooling instrument
B to 0 of 36 would give 0.00% to 9.64%, and that pooling is **not done in the
headline** because the two arms are different models on different banks and one
of them demonstrably cannot see the variable.

> **So the recommendation is: q8_0 is a defensible default for long-context
> serving, and the evidence bounds its verdict-level cost at under about 14%
> rather than showing it to be zero.** F16's throughput advice now has a quality
> dimension it did not have; it does not have a guarantee.

**The caveat that must travel with it.** q8_0 rewrites the text of roughly nine
answers in ten on the production model. Nothing in this experiment says the
rewrites are worse - the verdicts say they are not - but a serving change that
alters almost every output is not invisible to users, to caches, to regression
diffs or to anything downstream that compares strings.

**This does not change the relay.** `/var/lib/sparkrouter/serving.conf` has one
writer and serving flags are its decision, not this repository's (F39). What
E77 provides is the evidence for that decision.

### Two instrument faults, both declared

1. **`tools/score_e77.py` was wrong on its first run and reported
   `correct_to_wrong` = 0 on every arm.** `score_kw_eval` encodes `verdict` as
   `bool | None` - True, False, None - and the comparison was written against
   the strings `"correct"` and `"wrong"`, which never match, so the metric was
   structurally zero whatever the data said. It was caught by not believing a
   clean sweep of zeroes, and the fixed version finds `K18`. **Prediction 2
   would have scored FALSIFIED on an instrument that could not return anything
   else.** The line now carries a comment naming the domain.
2. **`tools/run_ps_eval.py` gained `--allow-busy-gpu`.** Its Rule 9 preflight
   refuses while any `llama-server` holds the GPU, which here is the production
   relay and cannot be stopped without sudo this account does not have - the
   same wall E76 hit. The **default still refuses**; the flag warns loudly and
   records `rule9_breach_acknowledged` and the offending pids in the output. The
   alternative was dropping instrument B, and a guard that cannot be
   acknowledged is a guard that gets bypassed with `--no-verify` instead.

### What this does NOT establish

- **Nothing about latency or throughput.** Rule 9 was breached, timings are void,
  and F16's throughput figures are quoted from F16 rather than re-measured. The
  prefill and decode half of E77 still needs the attended bench window.
- **Nothing about the `l` pack or contexts past 65,536 cells.** The relay serves
  98,304 and the saving above is a projection to it, not a measurement at it.
- **Nothing about hybrids.** Instrument B could not see the variable, so
  Qwen3.8's KV precision remains unmeasured in every sense that matters.

## E77 ADDENDUM PRE-REGISTRATION - the timing half, on a quiet GPU (2026-08-28, evening)

**Registered before the re-run starts.** E77's correctness half is complete and
unchanged; this completes the half that was declared void.

### Why this exists

E77 ran with the production relay resident. Rule 9 was breached **as registered**,
so every wall time, TTFT and throughput figure in `results/raw/e77-a-*.json` is
**void** - correctness is not a contended quantity, timing is. F16 recommends
`q8_0` KV for long-context work on **throughput** evidence, and this repository
has still never measured that throughput itself.

**The GPU is now genuinely quiet, measured:** `sparkrouter-llama` inactive, no
`llama-server` process, GTT 4.54 GiB, `vmstat` bi/bo 0, CPU 100% idle. That is
the condition the original run could not have.

### Design

Identical to E77 instrument A - same script shape, same pinned corpus
(`98dad04`, reproducing packs at 55,665 and 140,526 chars), same explicit `-fa on`
on every arm including f16, same `-c` per pack (s 32768, m 65536), workhorse
`Qwen3-30B-A3B-Instruct-2507-Q4_K_M`. Four KV precisions x two packs = 8 servers.

Rates are taken from the **server's own** `prompt eval time` and `eval time`
lines under `-lv 6`, not from client wall time, because the client figure
includes queueing and HTTP.

### Predictions, each naming the FIELD it is scored against

| # | prediction | scored against | falsifier |
|---|---|---|---|
| 1 | correctness reproduces the void run exactly - a quiet GPU changes no answer | `correct` per arm file: **9,9,9,8** at pack s and **12,12,12,13** at pack m, for f16/q8_0/q5_1/q4_0 | any arm differing |
| 2 | q8_0 is not slower to decode than f16 - the claim F16 shipped on | median **decode tok/s** (server `eval time`), q8_0 vs f16 | q8_0 slower than f16 by more than 5% |
| 3 | smaller KV decodes faster, monotonically | median decode tok/s ordered q4_0 >= q5_1 >= q8_0 >= f16 | any inversion larger than 5% |
| 4 | prefill is not materially affected by KV precision | median **prefill tok/s** (server `prompt eval time`), spread across the four | spread > 15% |

**Prediction 3 is the one likely to fail** and is registered because the
programme has assumed it: a smaller KV cache means less attention bandwidth per
token, but quantised KV also costs dequantisation work per step, and which
dominates on RADV/gfx1151 is exactly what has never been measured here.

### Decision rule

- **Prediction 1 fails** - stop. The re-run is not comparable to E77 and nothing
  timing-related may be read from it until that is explained.
- **q8_0 at least matches f16 on decode** - F16's recommendation ships as
  measured on this box, and E77's memory finding (~4.219 GiB freed at `-c 98304`)
  gains a throughput number beside it.
- **q8_0 is slower** - F16's recommendation gains a caveat: it buys memory and
  costs speed, and the trade must be stated in the routing guide rather than
  presented as free.

| 4 | prefill spread across KV types <= 15% | **HELD** - 14.06% at pack s, 5.27% at pack m |

**Prediction 1 is the control that makes the rest readable.** Eight arms
reproduced their correctness exactly against a run taken with the relay resident,
which says a contended GPU changed no answer - only the clock. That is the
premise Rule 9 rests on, and it had never been tested here.

**Prediction 3 held, but read the tolerance honestly.** q5_1 and q8_0 are
inseparable - 58.37 against 58.42 at pack s, 39.31 against 39.74 at pack m. The
monotonicity is real between f16 and the quantised group, and **not** within it.
Nothing here ranks q5_1 against q8_0.

### What this changes

**F16's q8_0 recommendation is vindicated on this box, and now carries a
measured caveat it did not have.** It is not a pure memory saving:

- **it BUYS decode** - +8.35% at 14,768 tokens, **+14.82%** at 37,752. The gain
  grows with context, which is the direction attention bandwidth predicts, and it
  is the tier long-context serving actually lives in.
- **it COSTS prefill** - -10.51% at pack s, -2.64% at pack m. The cost *shrinks*
  as context grows, so the two effects move in opposite directions with length
  and q8_0 gets strictly more attractive the longer the context.
- **it frees memory** - E77's correctness half measured ~4.219 GiB at the relay's
  `-c 98304`, and E77 already established q8_0 changes no verdict.

**For the relay's long-context tier the recommendation is now unambiguous on
three axes at once** - same answers, more decode throughput, less memory - with
one real cost, a slower first token on short contexts.

**Nothing is applied.** `serving.conf` has one writer (F39) and the flag decision
is the owner's. This is the evidence, not a change.

### What this does NOT establish

- **One model.** The workhorse only, `-c 32768` and `-c 65536`. Nothing here
  covers the relay's actual `-c 98304`, and the trend says the decode gain would
  be larger there and the prefill cost smaller - an extrapolation, not a
  measurement.
- **Single observations.** One run per cell, no repeats, so no noise band is
  quoted. F15's +/-1.5% single-run noise floor was measured on `llama-bench`,
  not on this harness, and is not imported here.
- **q5_1 vs q8_0 is not resolved** - see prediction 3 above.
- **Prefill numbers are cold-prefill only.** Every later request in a run reuses
  the cached pack prefix and prefills 32-45 tokens, which is dominated by fixed
  overhead and is excluded deliberately.

## E81 PRE-REGISTRATION - is it slot HISTORY, or is it PREFIX DISPLACEMENT? (2026-08-28)

**Registered before either arm runs.** No arm has been executed and no answer
read.

### Why this experiment exists

E80's addendum established that a router request served by the same
`llama-server` changes answers in the multi-round tool loop, and left a general
form untested: *"the answering slot's history affects outcomes, whether that
history is router calls or earlier tool loops."* `E05` diverged in R3, whose
answering server saw no router call, so something beyond router traffic is
unaccounted for.

**The general form is probably wrong, and this says why before testing it.**
Every answering request in this bank begins with the identical 8,807-character
pack. Prompt-cache reuse keys on the longest common prefix, so reordering items
changes which item ran last but not what the cache can reuse. A **router**
request is different in kind: it carries no pack at all, shares no prefix with
the answering prompt, and therefore displaces what the slot had cached.

So the hypothesis under test is narrower than "history matters":

> **H-DISPLACE: what changes an outcome is a request that shares NO PREFIX with
> the answering prompt, not the sequence of answering requests.**

| | |
|---|---|
| **which success question** | none directly - this is instrument work that decides how much of E79 and E80 is measuring the harness |
| **uncertainty reduced** | whether every multi-round tool figure in this repository needs an ordering control, or only an interleaving one |
| **decision that changes** | whether the E80 rule stays *"never share a server between router and answerer"* or widens to *"fix the item order too"*, which would be far more expensive |

### The two arms, both replaying R2's fixed decisions

Every arm uses `--router fixed` with `results/raw/e80-r2-decisions.json`, so
**no routing decision varies anywhere in this experiment.** The baseline is the
E80 control, which was run twice and was 24/24 byte-identical, so any change
here is the manipulation and not noise.

| arm | manipulation | what it isolates |
|---|---|---|
| **O1** | `--order reverse` | item ORDER, with no foreign prefix introduced |
| **O2** | `--interleave-dummy`, bank order | a router-shaped request before each item whose answer is **discarded** - foreign prefix, zero routing effect |

**O2 is the decisive arm.** It reproduces R2's request pattern exactly while
using R2's already-fixed decisions, so if displacement is the mechanism it
should reproduce R2's outcomes - including the two cells R2 alone got.

### Predictions, each naming the FIELD it is scored against

| # | prediction | scored against |
|---|---|---|
| 1 | **order does not matter** | O1 differs from the E80 control on **0 of 24** outcomes |
| 2 | order does not even change the text | O1 is byte-identical to the E80 control on **24 of 24** answers |
| 3 | **DECISIVE: displacement reproduces R2** | O2 `R09` = `off_by_calendar` and `E08` = `correct` - the two cells R2 alone produced |
| 4 | and reproduces it exactly | O2 differs from E80-R2 on **0 of 24** outcomes |
| 5 | the two manipulations are not the same thing | O1 and O2 differ from each other on **>= 1** outcome |

**Prediction 1 is registered as a NULL and I expect it to hold.** A null result
here is the useful one: it means the ordering control nobody has been running
was never needed, and the cheap rule E80 already wrote is sufficient.

### Registered decision rule, tie-break included

| observed | action |
|---|---|
| P1 and P3 both hold | **H-DISPLACE confirmed.** The E80 rule stands unchanged and is sufficient; `E05`'s R3 divergence is attributed to the same cause, since R3 offered the tool on twice as many band-E items and its loops carry non-pack tool-result context |
| P1 holds, P3 fails | displacement is not the mechanism either. **Both explanations die** and the instability returns to unexplained - say so and stop, rather than reaching for a third story |
| P1 fails - order alone moves an outcome | **the expensive outcome.** Item order is a live variable, every multi-round figure in E79/E80 needs an ordering control, and the E80 rule is insufficient. Report it loudly; it is the result that costs the most to have missed |
| **tie-break:** P1 fails AND P3 holds | both matter. Do NOT rank them from one run each - report both and register a replicate before any rule is written |
| O2's discarded router call errors on more than 1 item | the dummy is not clean. Fix before scoring |

## E81 RESULT - both mechanisms are real. Displacement reproduces R2 EXACTLY; order changes text deterministically. PREDICTIONS 1 AND 2 FALSIFIED. (2026-08-28)

All arms replay `e80-r2-decisions.json`, so **no routing decision varied
anywhere in this experiment.** One server, `-c 16384`, `-fa on`, Rule 9 breached,
wall times VOID.

| comparison | differing outcomes | byte-identical answers |
|---|---|---|
| **O2** (discarded router-shaped request) **vs E80-R2** | **0 of 24** | **24 of 24** |
| **O1** (reverse order) **vs the E80 control** | 1 of 24 (`R10`) | 22 of 24 |
| O1 vs its own replicate | **0 of 24** | **24 of 24** |
| O1 vs O2 | 3 of 24 | 17 of 24 |

### H-DISPLACE is confirmed, and the confirmation is exact

**O2 fired a router-shaped request before each item and threw the answer away.
It reproduced E80-R2 byte-for-byte on all 24 answers** - including the two cells
R2 alone produced, `R09` = `off_by_calendar` and `E08` = `correct`.

> **The routing had nothing to do with it. The request's mere presence did.**
> A request sharing no prefix with the answering prompt displaces the cached
> pack, and in a multi-round tool loop that is enough to change an answer.

### But my registered NULL was wrong, and order matters too

I predicted order would change nothing and gave a mechanism for it: every
answering request opens with the same 8,807-character pack, so reuse should key
on the same prefix regardless of sequence. **Predictions 1 and 2 are falsified.**

| item | bank order | reverse order | reverse, replicated |
|---|---|---|---|
| `R07` | `1074.47`, wrong | **`434.87`**, wrong | `434.87`, wrong |
| `R10` | `14 December 2025`, wrong | **HTTP 500**, transport_failed | HTTP 500, transport_failed |

**And reversal is deterministic.** The replicate is 24 of 24 byte-identical to
O1, so these are not flakes: the same order produces the same output twice, and
a different order produces a different output reproducibly.

`R10` is the one to look at twice. **A reproducible HTTP 500 that occurs under
reverse order and never under bank order** is a server failure contingent on
request history, not a random fault - and the same session saw one other HTTP
500 (E79 arm B, `E09`), also inside a tool loop. That is a concrete artefact for
anyone who wants to chase a `llama-server` bug; this experiment only records it.

### Scoring

| # | prediction | outcome |
|---|---|---|
| 1 | O1 differs from the control on 0 of 24 outcomes | **FALSIFIED** - 1, `R10` |
| 2 | O1 byte-identical to the control on 24 of 24 | **FALSIFIED** - 22 of 24 |
| 3 | **DECISIVE:** O2 `R09` = `off_by_calendar` and `E08` = `correct` | **HELD** |
| 4 | O2 differs from E80-R2 on 0 of 24 | **HELD** - and byte-identical too |
| 5 | O1 and O2 differ from each other on >= 1 | **HELD** - 3 |

### The tie-break fired, the replicate it demanded was run, and only now the rule

The registered tie-break: *"P1 fails AND P3 holds -> both matter. Do NOT rank
them from one run each - report both and register a replicate before any rule is
written."* That is exactly what happened, the replicate was run, and it settled
that the order effect is real rather than noise.

**The rule, now that it is earned:**

> **In a multi-round tool loop on one slot, both the request HISTORY and the
> item ORDER are live variables.** E80's rule - never share a server between a
> router and its answerer - is **necessary and not sufficient**. An arm's item
> order is part of its configuration and must be held constant across any
> comparison.

### What this costs E79 and E80, measured rather than feared

**Every arm in E79 and E80 ran in bank order.** The order variable was therefore
held constant across every comparison already made, and no headline moves.

The size of the effect is small and now measured: **reversal changed 2 of 24
answers' text and ZERO capability verdicts.** `R07` was wrong before and wrong
after; `R10`'s verdict change is a transport failure, not a capability one.

What it does touch is **per-item** claims. E79 and E80 name specific items as
converted or regressed, and those attributions are now known to be
order-contingent at about the 8%-of-items level for text and 0% for verdicts on
this bank. **The band totals and the between-arm comparisons stand; a claim
about one named cell carries this caveat.**

### What this does NOT establish

- **One bank, one reversal, one model.** Reverse is a single alternative order,
  not a sample of orders; a shuffle study would bound the effect properly and
  was not run.
- **The prefix-displacement mechanism is confirmed by REPRODUCTION, not by
  instrumentation.** No cache metric was read from the server. O2 reproducing R2
  byte-for-byte is strong, and it is still behavioural evidence.
- **`E05`'s R3 divergence is now attributable but not demonstrated.** R3 ran
  twice as many band-E tool loops, so its slot history differed - consistent
  with both mechanisms confirmed here, tested by neither.

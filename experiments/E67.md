## E67 - PREREGISTRATION: the H6 deterministic-date arm (2026-08-19)

**Registered BEFORE any run.** Written after building `tools/date_calc.py` and
`tools/run_h6_date_arm.py` and after reading the statutory rules, but before a
single model call. No arm has been run at the time of writing.

### The hypothesis and its two-sided falsifier

> **H6: Delegating deterministic subproblems to deterministic tools improves task
> reliability more cheaply than allocating additional model reasoning to them.**

Falsifier, as registered in the R&D programme's AMENDMENT 2: H6 is rejected if
tool delegation **fails to convert the known arithmetic failures**, OR if it
**introduces more new failures than it removes**. Both directions are counted;
neither is reportable alone.

### Design

Six L4 questions whose answer is a date - `P1 P2 P3 B1 N1 N2` - asked single-turn
against the L4 pack. Two conditions, same model, same session, same prompts
except that the treatment appends a four-line notice that date tools exist:

| condition | tools offered |
|---|---|
| control | no |
| treatment | yes - `add_period`, `last_day_of_month`, `date_diff` |

Single-turn rather than the E57 conversation, deliberately: this isolates the
arithmetic from the depth confound. **The consequence is that these scores are
NOT comparable to E63/E66's held-out numbers**, and the comparison that matters
is within-experiment, control against treatment on the same model.

**The tool cannot answer the question for the model.** `date_calc.py` exposes
three primitives and no domain helper - a test asserts that
`limitation_deadline`, `dsar_deadline` and friends do not exist. The model must
still choose the anchor date, the period and whether a last-day-of-month step
applies. Without that constraint H6 would be answered by construction.

### The mechanism this is really testing, and why P3 is the sharp case

F92 recorded gpt-oss-120b and a frontier arm giving the **identical** wrong date
on `P3` - 15 September 2026 against a correct 14 September 2026. Reading
STAT-LIM section 3 makes a second explanation available:

> "The period begins on the day after the cause of action accrued and expires at
> the end of the corresponding day in the sixth year following."

The breach is 14 September 2020, so the period begins 15 September 2020. Read
"the corresponding day" as corresponding to the period's START and six years
gives **15 September 2026** - exactly what both models answered. The registered
answer anchors on the ACCRUAL date instead.

**If that is the mechanism, no calculator fixes it.** The model calls
`add_period("2020-09-15", years=6)`, receives a perfectly correct answer to the
wrong question, and is now confidently wrong with a tool receipt to show for it.
That is why the arm records call ARGUMENTS, not just outcomes, and why the
classifier separates `wrong_args` from `result_ignored` - they have opposite
fixes.

### Predictions, each naming the FIELD it is scored against

| # | prediction | field |
|---|---|---|
| 1 | Offered the tools, the model actually uses them: `n_calls >= 1` on **at least 4 of 6** questions | per-result `n_calls`, treatment run |
| 2 | Treatment `correct` is **strictly greater than** control `correct` | top-level `correct`, both runs |
| 3 | **`P3` is NOT converted.** Its treatment `class` is `wrong_args`, not `correct` - the failure is anchor selection, not counting | `class` of the `P3` row, treatment run |
| 4 | **At least one new failure appears**: some question with `outcome == correct` in control is not `correct` in treatment | per-id `outcome`, both runs |
| 5 | Tool errors are non-zero but rare: `class_counts["tool_error"]` is **0 or 1** | `class_counts`, treatment run |

**Prediction 3 is the one worth being wrong about.** If `P3` converts to
`correct`, the F92 reading is wrong and the failure really was arithmetic - which
would be a stronger result for H6 than any of the others.

**Prediction 4 is registered as an expectation of HARM, not a hedge.** The
routing guide already records the workhorse as UNSAFE for conditional tool calls,
and a model that reaches for a calculator on a question needing none has been
made worse by the tool. Counting only conversions would hide it.

### Decision rule, registered now

Let `C` = questions converted wrong -> correct, and `N` = questions regressed
correct -> wrong. On this instrument: **`C > N` supports H6, `C <= N` rejects it**,
and `C == N == 0` means the tool was never engaged and the arm is void rather
than negative - re-run with the tool preamble strengthened before concluding
anything.

### Arms, in order

1. **workhorse Qwen3-30B-A3B** - fast, safe, no deadlock risk, and the arm where
   prediction 4 is most likely to fire.
2. **gpt-oss-120b** - the model that produced the F92 failure. 59 GiB, subject to
   the unexplained decode hang, so attended only.

Serving config is recorded per run in the result JSON (`server_extra`, `ctx`,
`max_tokens`, `max_rounds`, `full_offload_gate`) per Rule 8 / F39.

## E67 - RESULTS: the date tool rescues the weak model and DAMAGES the strong one (2026-08-19)

Preregistration is the section immediately above, banked in `b614c60` before any
model call. Two models, three conditions, temperature 0 throughout, same serving
config within each model.

| model | control | preamble-only | tools on | conversions `C` | regressions `N` | verdict |
|---|---|---|---|---|---|---|
| workhorse 30B-A3B | **0/6** | - | **4/6** | 4 | 0 (untestable) | supports |
| gpt-oss-120b | **5/6** | **5/6** | **4/6** | 0 | 1 | **rejects** |

### The workhorse arm: 0/6 -> 4/6

Every control cell is `no_call` and every control answer is wrong - and not only
by miscounting. `P3` grades `wrong_trigger`: it anchored on the 2 March 2023
discovery date rather than the breach. With the tools it converts `P1`, `P2`,
`B1` and `N1`, makes 13 calls and raises zero tool errors.

**Registered predictions 1, 2, 3 and 5 all held on this arm. Prediction 4 is NOT
SCORABLE and that is a design limit, not a pass.** It registered at least one
`correct -> wrong` regression, but a control of 0/6 makes `N` structurally zero
and the decision rule `C > N` trivially satisfied. **The harm direction of H6's
falsifier cannot be tested on a model sitting at the floor.**

**Prediction 3 held, and the call trace confirms the mechanism exactly.** `P3`
was registered as NOT converting because its failure is anchor selection rather
than arithmetic. The model passed
`add_period(date="2020-09-14", years=6, days=1)` - explicitly adding STAT-LIM's
"day after" - received a perfectly correct `2026-09-15`, then applied an
unjustified `last_day_of_month` to reach 30 September 2026. **Two legal errors,
both arithmetically flawless.** A calculator cannot fix a wrong question.

**An observation only the argument trace can see.** `P2` scores `correct` by the
WRONG ROUTE: the model counted the two months in sequence (the registered trap,
reaching 28 April) and then applied `last_day_of_month` to land on 30 April.
Answer-only grading records a clean hit.

### The gpt-oss-120b arm: 5/6 -> 4/6, and the falsifier fires

Control is 5/6 with `P3` the sole failure at **15 September 2026** - reproducing
F92 exactly. Offered the tools it drops to 4/6:

- **No conversions.** `P3` stays wrong and is `no_call` - the one question it
  gets wrong is the one question it does not reach for the tool on.
- **One regression.** `N2` goes from a correct 31 December 2026 to
  **1 December 2026**, `off_by_calendar` - and it made **no tool call** doing so.
- **It barely engages at all:** 1 call across 6 questions, against the
  workhorse's 13.

**Registered predictions 1, 2 and 3 are all FALSIFIED on this arm** (1 call not
4+; 4 correct not more than 5; `P3` is `no_call` not `wrong_args`). Predictions 4
and 5 held. `C = 0`, `N = 1`, so `C <= N` and **the registered decision rule
rejects H6 on this arm.**

### The regression is caused by the TOOLS, not by the sentence announcing them

`N2` regressed without any tool call, which leaves two candidate causes: the
four-line preamble, or the tools themselves. The `preamble-only` condition -
preamble appended, `tools` field withheld from the payload - separates them:

| condition | preamble | `tools` in payload | score | `N2` |
|---|---|---|---|---|
| control | no | no | 5/6 | correct |
| preamble-only | **yes** | no | **5/6** | **correct** |
| tools on | yes | **yes** | **4/6** | **wrong** |

**The preamble is exonerated; the tools field is not.** And the mechanism is
visible in the serverlogs: `add_period` appears **14 times** in the tools run's
rendered prompts and **0 times** in the preamble-only run's. Under `--jinja` the
tool schemas are rendered into the prompt the model actually sees, so offering a
tool changes behaviour on questions where the tool is never called.

This is Rule 8 / F39 arriving in a new place: **`tools` is part of the serving
configuration, not a free-standing capability, and a run that offers tools is a
different configuration even on the requests that never use them.**

### What E67 establishes, stated no wider than the evidence

**H6 is not a property of the task. It is a property of the model's baseline
competence at the subproblem.** The same tool, the same six questions, the same
temperature: it converts 4 for a model that could not count at all, and costs 1
for a model that could. Reported as a single average across arms it would have
read as "+3 net, H6 supported", which is exactly the wrong conclusion for the
model actually serving the difficult tier.

**What it does not establish.** n=1 per cell and six questions per arm, so a
single regression is a single observation - the direction is evidenced by the
three-condition control, the magnitude is not. Nothing here is a per-question
rate. And it says nothing about tasks other than date arithmetic.

### REPEATED: the regression is bit-identical across three runs

`N = 1` was one observation, and a recommendation was already circulating on it,
so the gpt-oss control/tools pair was re-run twice more the same afternoon:

| condition | runs | score | `N2` | calls |
|---|---|---|---|---|
| control | 3 | **5/6** every time | 31 December 2026, correct | 0 |
| preamble-only | 1 | 5/6 | 31 December 2026, correct | 0 |
| tools on | 3 | **4/6** every time | **1 December 2026**, `off_by_calendar` | 1 |

Every answer identical run to run, `P3`'s 15 September 2026 included.

**This retires exactly one hypothesis - sampling noise - and no others**, which is
F88 turned on our own result: a bit-deterministic arm reproduces its errors as
faithfully as its successes. Three identical runs buy no more generality than
one. The direction of the harm is now solid; its breadth is untested.

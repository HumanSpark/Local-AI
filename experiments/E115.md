## E115 PRE-REGISTRATION - is `--reasoning-effort` a DEFAULT or a HARD OVERRIDE? (2026-09-06)

**Registered before the run.** `results/raw/e115` does not exist.

### Why this experiment exists

`docs/plans/2026-09-06-serving-reasoning-effort-proposal.md` asks sparkrouter to
set `--reasoning-effort medium` for Qwen3.8-27B. The quality case is measured
and strong - E42 on the expert tier gives `off` 3/8, `low` 5/8, **`medium` 7/8**;
E101 gives `medium` 6 of 6 and 18 of 18 against `xhigh`'s 7 of 18 with 11
runaways for three times the tokens.

**The proposal names one thing that could reject it outright, and says to test
it before applying:** whether a per-request `reasoning_effort` still overrides
the server flag. If the flag is a hard override, then every caller currently
sending `xhigh` deliberately silently stops getting it - a behaviour change,
not a default change. Nobody has tested this.

It is the cheapest decisive measurement available: it gates a production change
whose evidence is otherwise complete.

| | |
|---|---|
| **which success question** | whether the proposed flag preserves caller control |
| **uncertainty reduced** | the one item the proposal says must be settled first |
| **decision that changes** | whether the proposal is applied, amended, or rejected |

### Design

Four cells, two server starts, `Qwen3.8-27B-Q4_K_M`, build `b10435`, greedy so
one sample per cell is a measurement rather than a draw, `--max-tokens 3072`,
two short prompts that reward deliberation without requiring it.
`tools/e115_effort_override_probe.py`.

| cell | server flag | request param | reads as, if the request overrides |
|---|---|---|---|
| A1 | `--reasoning-effort medium` | none | medium |
| A2 | `--reasoning-effort medium` | `xhigh` | **xhigh** |
| B1 | none | none | xhigh (the template default) |
| B2 | none | `medium` | medium |

**The B cells are a POSITIVE CONTROL and are not optional.** Without them,
"A2 looks like A1" cannot be told apart from "the metric cannot distinguish
medium from xhigh at all" - which is the vacuous-success shape this repo has met
repeatedly (E101's C1, E103's P0). B1 vs B2 must separate before A1 vs A2 means
anything.

Metric: reasoning characters emitted and completion tokens, compared as a RATIO
between cells, never as an absolute.

### Predictions, each naming the FIELD it is scored against

| # | prediction | scored against |
|---|---|---|
| 0 | **the control separates** - the metric can see effort at all | B1 `reasoning_chars` >= 2x B2, on both prompts |
| 1 | **HEADLINE: the request overrides the flag** | A2 `reasoning_chars` >= 2x A1, on both prompts |
| 2 | the flag is applied at all when nothing is requested | A1 `reasoning_chars` within 0.5-2x of B2 |
| 3 | the two xhigh paths agree | A2 within 0.5-2x of B1 |
| 4 | nothing hits the cap, so the ratios are real and not clipped | `finish_reason` is `stop` in all 8 generations |

### Registered decision rule

| observed | action |
|---|---|
| P0 and P1 hold | **the flag is a default, caller control is preserved.** The proposal's blocking item is cleared and it goes to the owner to apply |
| P0 holds, P1 fails | **the flag is a HARD OVERRIDE.** The proposal must be rejected or amended; report it that way and do not soften it |
| P0 fails | the probe measured nothing. No claim either way about A1 vs A2 - fix the metric, do not interpret the cells |
| any `finish_reason` = `length` | that generation is clipped and its ratio is void; re-run that cell with a larger cap before scoring |

### What this cannot establish

- **Nothing about the relay's real workload.** The proposal's second open item -
  whether the relay mostly serves short chat turns, where E101 found medium and
  xhigh indistinguishable - is untouched by this and stays open.
- Two prompts, one model, one build. It is a config-semantics probe, not a
  capability measurement.
- Nothing about whether `medium` is the right level; that is E42 and E101's
  question and it is already answered.

### E115 AMENDMENT 1 - declared BEFORE the ladder run (2026-09-06)

The four cells raise a question they cannot answer, and it changes the production
advice, so one more cell block runs before anything is written up.

**A2 (`xhigh` requested) is byte-identical to B1 (nothing requested).** Two
readings fit that equally:

1. `xhigh` was honoured, and the template default is `xhigh` - the repo's
   standing claim (CLAUDE.md, F140).
2. `xhigh` is not a value this template recognises, and an unrecognised value
   falls back to the default - in which case every caller "deliberately sending
   `xhigh`" has always been getting the default, and the proposal's blocking risk
   is empty for a completely different reason.

B2 already rules out "any per-request value is ignored", since `medium` was
honoured. It does not rule out "`xhigh` specifically is not recognised".

**Added:** one server, no flag, the `counting` prompt only, requesting each of
`minimal`, `low`, `medium`, `high`, `xhigh`, `max` plus a no-parameter control.
Roughly six minutes. **Prediction, scored against `reasoning_chars`:** at least
three DISTINCT values appear across the seven cells. If every level collapses to
two values, the level names are largely decorative on this template and the
production advice must say so.

## E115 RESULT - the flag is a DEFAULT, caller control survives, and the level names are not what they seem (2026-09-06)

`Qwen3.8-27B-Q4_K_M`, build `b10435`, greedy, `--max-tokens 3072`, two prompts,
`finish_reason` `stop` in all eight generations.

| cell | server flag | request | counting | scheduling |
|---|---|---|---|---|
| A1 | `--reasoning-effort medium` | none | 633 / 509 | 1248 / 746 |
| A2 | `--reasoning-effort medium` | `xhigh` | **337 / 220** | **775 / 404** |
| B1 | none | none | **337 / 220** | **775 / 404** |
| B2 | none | `medium` | 633 / 515 | 1131 / 691 |

*(reasoning characters / completion tokens)*

### THE ANSWER to the question that gated the proposal

> **`--reasoning-effort` is a DEFAULT, not a hard override.** A2 is byte-identical
> to B1 on both prompts, so a request-level value wins over the server flag. And
> the flag is genuinely applied when nothing is requested, because A1 differs
> from B1. **Callers keep the ability to ask for more, which is what the
> proposal's blocking item required.**

### Scoring, and the direction I got wrong

| # | prediction | outcome |
|---|---|---|
| 0 | control separates - B1 `reasoning_chars` >= 2x B2 | **FALSIFIED** |
| 1 | HEADLINE: A2 >= 2x A1 | **FALSIFIED** |
| 2 | A1 within 0.5-2x of B2 | held (1.00x, 1.10x) |
| 3 | A2 within 0.5-2x of B1 | held - identical |
| 4 | all eight generations `stop` | held |

**P0 and P1 both encoded "xhigh produces more reasoning than medium", and the
data says the opposite.** `medium` emits 1.6-1.9x MORE than the default on both
prompts. The control did separate - by 1.88x and 1.61x, in the other direction -
so the probe measured what it was built to measure and my arithmetic
inequalities pointed the wrong way. They are scored FALSIFIED rather than
reinterpreted to fit.

That inversion does not contradict E101's `xhigh` runaways (11 of 18 hitting the
cap on long coding tasks). Terse on short prompts and non-convergent on long
ones is one behaviour, and it is [[F141]]'s shape: looping is non-convergent
deliberation, not verbosity.


## E115 AMENDMENT 1 RESULT - only three levels exist, and the other three are a 500 (2026-09-06)

Seven levels, one prompt, one server, no flag.

| request | reasoning chars | |
|---|---|---|
| `(none)` | 337 | |
| `minimal` | - | **HTTP 500** |
| `low` | 542 | |
| `medium` | 633 | |
| `high` | - | **HTTP 500** |
| `xhigh` | **337** | identical to `(none)` |
| `max` | - | **HTTP 500** |

Distinct values `[337, 542, 633]`, so the registered prediction of at least
three held.

**The template says so itself**, and it is better evidence than the measurement:

```
Unexpected reasoning effort minimal. Supported types are xhigh (default), medium, and low.
```

Two consequences, both production-relevant:

1. **The ambiguity is resolved.** `xhigh` is recognised AND is the default, so
   A2 == B1 is "xhigh honoured", not "xhigh ignored". The repo's standing claim
   is confirmed from the template rather than by inference.
2. ⚠️ **`llama-server --reasoning-effort` advertises `minimal|low|medium|high|
   xhigh|max`. This model's template accepts three of them and RAISES on the
   rest** - the request fails with HTTP 500 rather than degrading. **Setting
   `--reasoning-effort high` on the unit, a reasonable pick from the help text,
   would fail every request to that model.** The proposal's `medium` is one of
   the three valid values, so the proposal itself is safe; the flag's documented
   range is not.

The probe originally died on the first rejected level and was fixed to record a
rejection as data - an error is the answer here, and a prober that crashes on it
hides exactly the hazard worth knowing.


## E115 AMENDMENT 2 RESULT - the determinism the headline rests on, measured (2026-09-06)

E115's cross-cell inference assumes greedy decoding reproduces here. That is not
a general property of language models: float addition is not associative, so
batch composition, split-k reductions, kernel choice and MoE routing can move
low bits and flip a near-tie argmax.

Cell A1 re-run on two fresh server processes:

| prompt | rep 1 | rep 2 | identical |
|---|---|---|---|
| counting | 633 / 509 | 633 / 509 | **yes** |
| scheduling | 1248 / 746 | 1248 / 746 | **yes** |

Both also match the original A1. **Cross-restart determinism holds for this
configuration** - `-np 1`, one request in flight, a dense model, one build. It
would NOT be expected to hold on the production relay, which serves several
slots with continuous batching.

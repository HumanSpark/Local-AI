## E128 - can the PRODUCTION gateway take `reasoning_effort` per request? (2026-09-07)

Run against the live gateway on `127.0.0.1:8400`, model id `local_smart`, three
requests, temperature 0, same prompt as E115's `scheduling` cell. Not
pre-registered: a three-request read-only probe to decide whether a production
runtime upgrade was needed at all.

| request | completion tokens | reasoning chars | finish |
|---|---|---|---|
| a) no field | 404 | 775 | stop |
| b) `reasoning_effort: medium` | **404** | **775** | stop |
| c) no field again | 404 | 775 | stop |

**The field is accepted and silently ignored.** No error, and byte-identical
output to sending nothing. (a) and (c) bracket (b), so the request-history effect
measured in E119 cannot account for it.

### Consequences

1. **The upgrade is required.** Neither route to `medium` works on the gateway's
   build `067de9371` (2026-07-03): the server flag is fatal to it (the process
   exits on an unrecognised argument - the 5-minute outage at 08:03) and the
   per-request field does nothing. `--reasoning-effort` and the template plumbing
   that reads `reasoning_effort` arrived together upstream, after this build.
2. **Production is confirmed running at `xhigh`, measured rather than inferred.**
   775 reasoning characters and 404 completion tokens is exactly what the bench
   build produced for `xhigh` on this prompt (E115 cell B1). The same model and
   prompt reproduce across two different builds, which also says the default the
   proposal targets is the one actually in force.
3. **A silently ignored field is worse than a rejected one.** Any caller setting
   `reasoning_effort` against this gateway today gets no error and no effect. That
   is the same class as E123's inert flag on the two MoE models, and it is why
   "the request was accepted" is never evidence a setting took hold.

## E71 PRE-REGISTRATION - S-H2: the gpt-oss-120b load/decode soak (2026-08-19)

**Registered BEFORE any run.** This is item 1 of AMENDMENT 3's revised execution
order: S-H2 moved from last to first because C-H2, S-H1 and every unattended role
for gpt-oss-120b gate on it.

### Why this experiment exists (required of every experiment from 2026-08-19)

| | |
|---|---|
| **which success question** | *What percentage of my Claude Sonnet coding workload can I hand to the local machine without supervising it?* - "without supervising" is the clause S-H2 gates. A model that hangs unpredictably cannot take unattended work at any capability |
| **uncertainty reduced** | the fault rate is currently `1 observation, denominator disputed`. After 25 controlled cycles it is a rate with an interval, and the fingerprint is either confirmed killable or not |
| **decision that changes** | whether gpt-oss-120b may be a C-H2 batch arm at all, and whether the C-H2 harness needs a first-token watchdog. Both are currently blocked on a guess |

### The hypothesis, from AMENDMENT 3 / the owner's workplan

> **S-H2: gpt-oss-120b can only become an unattended service once the unexplained
> load/decode failure is either understood or shown to be sufficiently rare under
> repeated controlled loading.**

**This soak does not attempt a diagnosis.** It measures a RATE and a
FINGERPRINT. A mechanism for the Vulkan/RADV stall is out of scope and is not
claimed either way by the outcome.

### Why this is safe to run unattended, stated before it runs

`docs/2026-08-19-gptoss120b-decode-hang.md` establishes on six axes that the
observed fault is **not** the amdgpu suballocator deadlock: process state `S` not
`D`, cleared by `pkill -x` in under 5s, VRAM 1.90 GiB and never parked at the
documented 2.00 GiB, struck *after* a complete load rather than during one, model
fully resident, and recovered with no power cycle. **The box was never at risk.**

That is what makes a repeated-load soak an unattended job rather than an attended
one. The abort rule below exists because "not that deadlock, observed once" is
not "never that deadlock".

### Design

25 iterations. Each iteration is a complete independent cycle: start
`llama-server` on the 3-shard `gpt-oss-120b-mxfp4` at `-c 8192 -np 1`, poll
`/health` to a 900s ceiling, send ONE trivial streaming prompt
(`max_tokens` 32, hard 180s request timeout), tear the server down, settle 10s.

Serving config, declared per Rule 8 / F39: `llama.cpp/wt/b10435`, `-c 8192`,
`-np 1`, `--no-webui -v`, temperature 0, default thinking, Vulkan/RADV gfx1151,
kernel 7.0.0-28. No `-b`/`-ub` overrides - the F72 flags are a REMEDY to test
later if the fault reproduces, not part of the baseline measurement.

**The prompt is deliberately trivial** (`Reply with exactly the word: ready`).
This measures the load-and-first-decode path, not capability. A capability
figure must never be read out of this run.

**Streaming, so time to FIRST token is stamped separately from completion.** A
non-streaming call cannot distinguish a stalled decode from a runaway
generation: both are one long silence. That distinction is the whole point.

### Pre-registered outcome classes, one per iteration

| class | condition |
|---|---|
| `ok` | health reached, first token arrived, generation completed |
| `load_timeout` | `/health` never returned 200 within 900s |
| `server_crashed` | process exited during load |
| `stalled_before_first_token` | healthy, request accepted, **no token** before the 180s timeout - the E61 shape |
| `tokens_then_no_termination` | first token arrived, generation never ended - the F71 shape |
| `unclear` | completed with zero content |

### ABORT RULE, and it is not advisory

If any iteration's server survives `SIGKILL` for 30 seconds, or if
`mem_info_vram_used` is sampled twice five seconds apart at exactly
2,147,483,648 bytes, the soak **stops immediately**, writes what it has, and
records `possible_deadlock`. It does not proceed to the next iteration. Hammering
a wedged GPU is how a recoverable fault becomes a power cycle.

Results are written to disk after EVERY iteration, so a wedge still leaves the
evidence for the iterations that completed.

### Predictions, each naming the FIELD it is scored against

| # | prediction | scored against |
|---|---|---|
| 1 | at least one iteration fails to reach `ok` | `iterations_failed`, expected >= 1 of 25 |
| 2 | no iteration matches the deadlock fingerprint | `possible_deadlock`, expected 0 |
| 3 | load time does not degrade across the run | `load_s`: median of the last 5 within 25% of the median of the first 5 |

**Prediction 1's basis, stated so it can be judged rather than believed.** The
fault was seen once in the loads of 2026-08-19 and the denominator has grown with
every clean load since (E63, E64, E67, E68, E69). At p = 1/12, P(zero failures in
25) is 12.4%; at p = 1/8 it is 3.5%. So prediction 1 is well-founded and
genuinely falsifiable - a clean 25 is an informative miss, not a formality.

**Prediction 3 exists because a soak can fail in a way a rate cannot see.** If
loads get progressively slower - a leak, fragmentation, thermal - the run could
be 25/25 `ok` and still disqualify the model from an unattended role.

### Pre-registered decision rule - these are ENGINEERING CHOICES, recorded as such

| observed | S-H2 verdict |
|---|---|
| any `possible_deadlock` | **disqualified outright**; soak stops; the memory-edge doc governs |
| 0 failures in 25 | 95% upper bound on the fault rate is **11.3%**. Cleared for SUPERVISED batch use. **Not** cleared for unattended production without a watchdog, because 11.3% is not a small number |
| >= 1 failure, all killable, all `stalled_before_first_token` | cleared for unattended use **behind a watchdog only**, and the observed fingerprint specifies that watchdog: a first-token deadline, then kill and restart |
| >= 1 failure of a NEW shape | the shape is the finding; no clearance until it is classified |

**A soak cannot produce a clearance for unattended use on its own.** The best
available outcome here is "rare, killable, and detectable by a watchdog" - which
is a clearance for a SYSTEM containing a watchdog, not for the model. That
distinction is F86's model-versus-system separation applied to reliability.

**Evidence to be written:** `results/raw/e71-soak-*.json` (incremental, one
record per iteration) and one `.serverlog` per iteration, retained in full for
any iteration that is not `ok`.


## E71 RESULT - 25/25 clean, and PREDICTION 1 IS FALSIFIED (2026-08-19)

Serving config as registered: `llama.cpp/wt/b10435`, `gpt-oss-120b-mxfp4`
(3 shards, 59.03 GiB), `-c 8192 -np 1 --no-webui -v`, temperature 0, default
thinking, Vulkan/RADV gfx1151, kernel 7.0.0-28. 25 independent load / smoke /
teardown cycles, 10.0 minutes wall.

| field | measured |
|---|---|
| `iterations_ok` | **25 / 25** |
| `iterations_failed` | **0** |
| `possible_deadlock` | **0** |
| `by_outcome` | `{"ok": 25}` |
| `load_s` median (min / max) | **22.02s** (22.01 / 24.02) |
| `load_s_first5_median` -> `last5` | 22.04 -> 22.02, drift **-0.1%** |
| `ttft_s` median | 0.88s |
| teardown | `sigterm` on all 25 - none needed `SIGKILL` |
| GTT peak | 63.06 GiB, identical on every iteration |

### Scoring, against the fields registered

| # | prediction | outcome |
|---|---|---|
| 1 | at least one iteration fails to reach `ok` | **FALSIFIED** - `iterations_failed` = 0 |
| 2 | no iteration matches the deadlock fingerprint | **HELD** - `possible_deadlock` = 0 |
| 3 | last-5 `load_s` median within 25% of first-5 | **HELD** - -0.1% |

**Prediction 1 was registered with its own arithmetic** (at p = 1/12, P(zero in
25) = 12.4%), so a clean run was a declared possibility rather than a surprise
being explained away afterwards. It is recorded as a miss.

### Two things the run measured that were not what it set out to measure

**1. `ok` did not mean "answered".** All 25 iterations returned 31 stream
chunks, 130 reasoning characters and **an empty content string**. The registered
`max_tokens` of 32 is entirely consumed by gpt-oss's reasoning phase, so no
iteration emitted a single content token. What 25/25 establishes is that the
**load-and-decode path runs and the request terminates cleanly** - which is
precisely the path the 2026-08-19 fault broke (logging stopped, zero tokens, a
754.95s hang) - and nothing about answer quality. Stated rather than corrected,
because the registered design said 32.

**2. The determinism is total.** 31 chunks, 130 reasoning characters, 63.06 GiB
GTT and a 22.0x second load on **every one of 25 separate processes**. That is
F88's bit-determinism reproduced on a different instrument, and it is why a
repeat of this soak buys very little: the arm reproduces its behaviour exactly,
so more of the same conditions is not more evidence.

### THE WARM/COLD CONFOUND WAS SUSPECTED AND THEN MEASURED AWAY

Mid-run I recorded a concern that 22.0s loads were page-cache warm while the
fault struck a cold load, which would leave the soak with little power against
the thing it was measuring. **Two corrections, both from the record rather than
from reasoning:**

- **117.68s is E64's folder-tier cold REQUEST latency, not a model load.** E64
  records `Model load 22.0s` in the same line. The soak's 22.02s median is the
  documented figure reproduced to two decimal places, not a warm shortcut.
- **A direct probe settles it.** Two further iterations with all three shards
  evicted from the page cache first (`posix_fadvise(DONTNEED)`, no root needed;
  `buff/cache` 51 -> 26 GiB, verified) loaded in **22.04s and 22.02s** -
  indistinguishable from warm. Load time on this box is dominated by device
  upload, not by disk.

So there is no warm/cold distinction to correct for, and the larger cold soak
that concern would have justified was cancelled before it consumed GPU time.
The same probe at `max_tokens 512` answered correctly (`"ready"`, 54 chunks,
234 reasoning characters, 1.97s) - which is where the 512 budget below comes
from.

### S-H2 VERDICT under the registered decision rule

The `0 failures in 25` row fires: the exact 95% upper bound on the fault rate is
**11.29%**. Per the rule registered before the run -

> **Cleared for SUPERVISED batch use. NOT cleared for unattended production
> without a watchdog**, because 11.3% is not a small number.

**The soak cannot do better than that and it is important to say why.** A rate
this low needs a sample this instrument can supply, so the bound is the honest
limit of 25 observations - not a judgement about the model. E72 addresses
exactly that and nothing else.

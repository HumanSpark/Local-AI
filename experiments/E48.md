## E48: the long-context ladder - E41 saturated at 8% of trained context, so go the rest of the way (2026-08-16, pre-registered before any run)

**Why this exists.** E41 swept the L3 pack at 0, 4 and 9 distractors and
returned **12/12 at every size with zero `wrong_document`**. Its registered
falsifier fired, and its own text records what that obliges: *"the boundary has
not been found rather than that there isn't one - the next probe would have to
go further out"*. This is that probe.

The number that makes it necessary: Qwen3.8's trained context is **262,144
tokens**, and the largest pack ever put to it in this repo is E41's n=9 at
**21,217** - **8.1%**. Every claim this programme makes about knowledge work
rests on packs that fit in a twelfth of what the model is built to read. The
driving question is whether this box does real professional work, and real
engagement folders are not three pages.

**ONE VARIABLE CHANGES: the size of the haystack.** The twelve questions,
their reasoning and their keys are derived from `QUESTIONS_L2` in code, and
`tools/validate_ps_eval_l3.py` asserts that equality mechanically. Re-run
2026-08-16 with the extended corpus: it still passes, 119 distractors defined,
**zero distractor/real figure clashes**, and all three synthetic respondents
still separate (`PERFECT` 12 correct, `WRONG_DOCUMENT` 9 wrong_document,
`VAGUE` 11 wrong).

### The corpus extension, and the proof it did not disturb E41

`spikes/ps-eval/corpus_l3.py` grew from 9 distractor agreements to **119**,
enough for a pack of ~244K tokens. Three things were done to keep E41's arms
usable as the baseline of this ladder rather than merely comparable:

1. **The nine original specs are literal and untouched.** The extension only
   adds ids.
2. **`build_pack_l3` now selects in DECLARATION order, not sorted order.** This
   is a defect fix, not a preference: the selection was `sorted(DISTRACTORS)[:n]`,
   a STRING sort, under which `"DIS-10"` precedes `"DIS-02"`. The moment the
   corpus passed nine agreements that would have silently changed which
   distractors every small pack contains - including E41's - and no score would
   have shown it.
3. **Byte-identity is asserted, not assumed.** The n=0, 4 and 9 packs were
   sha256'd before the change and re-hashed after:

| n | chars | sha256 (before == after) |
|---|---|---|
| 0 | 13,221 | `b93d23d1…` IDENTICAL |
| 4 | 49,076 | `9a700a42…` IDENTICAL |
| 9 | 93,920 | `582cb8e5…` IDENTICAL |

**The new distractors are combinatorial (22 Irish place names x 5 trades), not
typed out.** 110 hand-written tuples is 110 chances to reuse a real figure, and
that is the one error no score would reveal - a distractor sharing the real
500,000 cap makes a wrong-document answer grade as *correct*. Figures are
derived by index arithmetic that cannot leave `FIGURE_RANGES`, supplier names
are unique by construction, and the import-time disjointness assertion still
runs. Generation is a reason to trust the input, not a reason to drop the check.

**The interleave was rebuilt so the real documents stay buried.** Appending 110
distractors after `POL-3.1` would have put every real document in the first 8%
of the pack and turned the tier back into a reading-order test. Eleven
insertion points spread the extension either side of the real documents, filled
round-robin so any prefix is spread rather than front-loaded. Measured:

| n | pack chars | est. tokens | MSA-2024 sits | last real doc |
|---|---|---|---|---|
| 9 | 93,920 | 21,217 (measured) | 17.6% in | 94.1% |
| 29 | 273,223 | ~61,700 | 18.9% in | 94.6% |
| 59 | 542,144 | ~122,500 | 19.4% in | 92.5% |
| 119 | 1,079,950 | ~244,000 | 18.1% in | 91.3% |

Token estimates use **4.427 chars/token, E41's MEASURED ratio on this exact
corpus** - not a constant. They are estimates and are labelled as such; the
run records the real figure. This is the E41 AMENDMENT 1 lesson: a chars-based
estimate was wrong by 4,392 tokens there and must never again decide whether a
pack fits.

`thinking=low` on every rung, matching E41 AMENDMENT 1, so the ladder is

**KV cost is known-safe.** `-c 262144` on this DeltaNet hybrid carries KV for

### A silent-truncation guard now exists, because this experiment could not exist without it

`tools/run_ps_eval.py` had **no context preflight**. An oversized pack would
have been truncated from the front by llama-server, the model would have
answered from a folder whose opening documents were gone, and it would have
graded as a capability failure - F20 exactly, at 244K tokens where nobody would
spot it by eye. Added `count_tokens()` (the SERVER's tokenizer, never a
chars estimate) and `assert_context_fits()`, which refuses to run when
prompt + `max_tokens` exceeds `-c` and reports the overflow in tokens. The
measured headroom is recorded in every output as `context_preflight`.

**The same gap exists in three sibling runners** - `run_coding_eval.py`,
`run_writing_eval.py` and `spikes/closed-record/run_matters.py`, all of which
have run `max_tokens` of 100,000 or more against a 131,072 context. It is NOT
being fixed in this pass, deliberately: queues 14, 13, 12, 9 and 11 are chained
to invoke those exact scripts unattended over the next several hours, and an
untested edit to a script that cannot be smoke-tested while the GPU is busy is
how a queued arm dies at 3am. TODO: add the preflight to those three.
Why: same silent-truncation class, and two of them run within 31,072 tokens of
their context ceiling. Trigger: this registration; do it when the queue drains
and each can be smoke-tested live. `tooluse_harness_v2.py` is not at risk -
`max_tokens` is 1,200.

### E46 RESULT - the control REPRODUCED, and request SEQUENCE POSITION is the cause

Every cell ran E43 arm B's exact config (`thinking=xhigh`, `max_tokens 24,576`,
temperature 0). Only the number of requests preceding `m12` changed. The
`m12` prompt is byte-identical in all three - `prompt_tokens` is **755**
everywhere.

| cell | m12 is request | completion tokens | seconds | answer sha256 | chars |
|---|---|---|---|---|---|
| 1: m12 alone | 1 of 1 | 3,645 | 301.0 | `23038d6b0a77bbfc` | 2,858 |
| 2: m11,m12,m13 | 2 of 3 | 3,950 | 327.7 | `8b87187d40cabe0b` | 2,657 |
| **3: all 13 (CONTROL)** | **12 of 13** | **3,222** | **268.1** | **`9979e5aa040e731b`** | **2,506** |
| E43 arm B (the original) | 12 of 13 | **3,222** | - | **`9979e5aa040e731b`** | - |

**PREDICTION 1 HELD, exactly. Cell 3 is BYTE-IDENTICAL to E43 arm B** - same
sha256, same completion-token count. Reproducing the sequence position
reproduces the answer bit for bit.

**Three sequence positions, one prompt, THREE DIFFERENT ANSWERS at temperature
0.** This confirms the amended hypothesis and closes the question E43-vs-E44
opened.

**Mechanism.** llama-server reuses the KV cache prefix shared with the
preceding request. How much of the prompt is recomputed - and in what batch
boundaries - therefore depends on what was asked before it. Floating-point
accumulation is not associative, so a differently-chunked prefill yields
marginally different logits, and at temperature 0 a marginal difference is
enough to flip a token choice, after which the generations diverge. Nothing
here is random: each sequence is individually reproducible, which is why cell
3 reproduced.

**What this corrects.** F59 recorded local temperature-0 runs as deterministic.
That is true only in the sense the tests established it - the same sequence
re-run gives the same answers. It is NOT true that a given prompt has a single
temperature-0 answer on this server. Any comparison that puts the same prompt
at different positions in different arms is comparing two things, and the
earlier E43-vs-E44 divergence I nearly wrote up as a `-c` effect was exactly
that. Recorded as F70.

**Operational rule this produces:** an arm's matter ORDER is part of its
config. Two arms are comparable only if each prompt occupies the same
sequence position in both. E41's scale sweep and E43's four arms both satisfy
this by construction; it was never checked before, it was luck.

## E48 arm B: is the ~100K prefill wall a TUNABLE or the driver? (2026-08-17, pre-registered before any run)

**Why this exists.** E48's n=59 and n=119 rungs both killed the GPU during
prompt processing (F72), between 96,286 and 110,622 tokens. That is currently
recorded as a hardware ceiling, and the difference between "a hardware ceiling"
and "a setting we had wrong" is the difference between telling a client this box
cannot read a 300-page pile and telling them it can.

**The hypothesis.** A RADV context cancellation is what a driver does to a
compute dispatch that runs too long. llama-server submits prefill in `n_ubatch`
chunks, and both failing runs used the defaults - **confirmed from the
serverlog, not assumed: `n_batch = 2048`, `n_ubatch = 512`.** Quartering the
micro-batch quarters the work in each dispatch.

**ONE VARIABLE CHANGES: `-b 512 -ub 128`.** Everything else reproduces E48's
n=59 rung exactly - same pack, same 12 questions, `-c 262144`, `thinking=low`,
`max_tokens 4096`, temperature 0, b10435. The control is already measured: the
same rung at default batch died at n_tokens 96,286.

**A capability the runner did not have.** `tools/run_ps_eval.py` had no way to
pass server flags, so `--server-extra` was added, recorded in the output as
`server_extra` so an arm that changed a serving flag cannot be silently compared
against one that did not (Rule 8). Smoke-tested before this registration:
flags confirmed reaching the server as `n_batch = 512, n_ubatch = 128`, and
the value round-tripped into the result JSON.

**A confound named in advance, because F70 predicts it.** Changing `-ub` changes
how prefill is chunked, and F70 established that different chunking gives
different floating-point accumulation and therefore, at temperature 0, can flip
a token. **So arm B's ANSWERS are not expected to be byte-identical to a
default-batch run even where both complete.** The primary measurement here is
therefore whether it completes, not what it scores. The smoke test already
showed this: L3 n=0 at `thinking=off` scored 9/12 with the reduced batch where
the equivalent default-batch cell scored 8/12. Same direction, different
number, exactly as F70 says it should be.

### Predictions (registered before the run). The FIELD is named in each.

1. **PRIMARY: the count of `outcome == "transport_failed"` at n=59 is 0** - the
   run completes. This is the whole experiment. Registered as a positive
   because quartering the dispatch is the standard mitigation for a watchdog
   cancellation, though I hold it at moderate confidence rather than high.
2. **If it completes, `correct` is 10-12.** Not pinned at 12: scale did not
   degrade this model at n=29 (12/12), but F70's chunking effect can move
   individual answers.
3. **Prefill throughput is LOWER than the 49.57 tok/s measured at default
   batch**, read from the serverlog's `prompt processing ... tokens per second`.
   Band: **15-45 tok/s**. Smaller dispatches are less efficient; the trade is
   throughput for survival.
4. **If it does NOT complete, the serverlog's `stop processing: n_tokens` lands
   within ±20% of 96,286** (77,029 to 115,543). A death at a substantially
   different point would mean the mechanism is neither batch size nor a fixed
   token limit, and I would say so rather than fit a story to it.

**Not predicted:** which individual questions change answer relative to the
default-batch runs.

**Arm B2, conditional and registered now so it is not invented later:** if arm B
completes, the same flags run at n=119 (236,122 tokens). That tests whether the
mitigation scales or merely moves the wall. If arm B fails, B2 does not run.

**Falsifier: if arm B dies within ±20% of 96,286 tokens, batch size is not the
mechanism**, F72 stands as written, and the honest report to a client is that
this hardware cannot read a document of that size in one request regardless of
what the model is capable of. That is a useful answer, not a failed experiment.

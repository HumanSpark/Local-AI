## E111 PRE-REGISTRATION - does the THREE-ARM bank discriminate? (2026-09-06)

**Registered before the bank has ever been served.** `results/raw/e111` does not
exist. Bank: `spikes/coding-eval/expert_tasks_v3.py`, 4 tasks, tier `expert3`.

### Why this experiment exists

E110 answered the previous version of this question with a 7/7 (F150). Every
expert2 task had been proved to defeat a NAIVE solution, and that turned out to
be necessary and nowhere near sufficient - a competent model does not write the
naive solution, it writes the correct one.

So `expert3` raises the admission standard, per the owner's decision of
2026-09-06: every task must additionally defeat a **competent-but-subtly-wrong**
solution - one a good engineer would plausibly write, idiomatic and
correct-looking, wrong on a single corner. `tools/validate_expert_tasks_v3.py`
refuses the bank unless all three arms behave, and it reports the bank usable
as of 2026-09-06.

The subtle corners are **not imagined**. Each is the shape of a failure this
repo has measured:

| task | subtle corner | measured source |
|---|---|---|
| `billing_schedule` | anchor drift in month arithmetic; also an inclusive day count | F92, F89 |
| `peak_load` | a sweep sorted by time alone, so touching half-open intervals read as overlapping | F89 |
| `clear_days_deadline` | normalising the start to a business day before counting from it | F92, F146 |
| `window_mode` | incremental counts plus a per-window scan - correct, and too slow | F144, F149 |

| | |
|---|---|
| **which success question** | the instrument again - whether a three-arm standard produces a bank that is not saturated |
| **uncertainty reduced** | where the incumbent lands, which sets whether the recipe can be used to write the remaining tasks |
| **decision that changes** | whether to write more tasks in this style, or revise the standard a second time |

### Design

One arm. `Qwen3.8-27B-Q4_K_M`, `--task-set expert3`, `-c 32768 --max-tokens
24576 --thinking medium`, build `b10435`, `--exec-timeout 15`, quiet GPU -
**identical to E104, E105 and E110**, so the number is directly comparable to
7/8 on the original expert tier and 7/7 on expert2.

### Predictions, each naming the FIELD it is scored against

| # | prediction | scored against |
|---|---|---|
| 1 | **HEADLINE: the bank is not saturated** | incumbent `passed` **<= 3** of 4 |
| 2 | it is not impossible either | incumbent `passed` **>= 1** of 4 |
| 3 | the complexity gate is the hardest thing here | `window_mode` outcome is NOT `pass` |
| 4 | the plainest task is the one it gets | `billing_schedule` outcome IS `pass` |
| 5 | the tasks cost real reasoning, unlike expert2's 2,417 mean | mean tokens/task **> 5,000** |
| 6 | the harness holds | `no_code` and `transport_failed` counts both **0** |

**P1 is again registered in the direction that costs the most to be wrong
about.** A 4/4 means the second standard failed the same way the first did, and
that is worth finding at four tasks rather than at thirty.

P5 is the owner's cheap pre-filter turned into a scored prediction: expert2's
tasks averaged 2,417 tokens and the original expert tier 9,350, and a task the
incumbent finishes in under ~5,000 tokens is very unlikely to discriminate.

### Registered decision rule

| observed | action |
|---|---|
| 1-3 of 4 | **the recipe works.** Write the remaining tasks to the three-arm standard |
| **4 of 4** | **saturated again. STOP.** Three arms is still not enough; do not write more until the standard changes a second time |
| 0 of 4 | too hard to discriminate at this level. Label the tier and keep it; it measures a band below this model |
| any `no_code` | prompt defect, not capability - the task text does not determine the answer, and that is a bug in the task |

### What this cannot establish

- **One model, one run, 4 items.** It locates the control, nothing more.
- **A pass is "passes hidden tests", not "good code".**
- Nothing about the other challengers; they are not run.
- Nothing about whether the bank discriminates between two COMPETENT models -
  that needs a second model, and it is the question E110 proved this repo had
  not yet asked properly.

## E111 RESULT - the three-arm bank is SATURATED TOO. Predictions 1, 3 and 5 falsified; the stop rule fires again. (2026-09-06)

One arm, `Qwen3.8-27B-Q4_K_M`, `--task-set expert3`, `-c 32768 --max-tokens
24576 --thinking medium`, build `b10435`, `--exec-timeout 15`, quiet GPU -
identical to E104, E105 and E110.

| task | axis | outcome | tokens | wall |
|---|---|---|---|---|
| `billing_schedule` | date arithmetic + fixed anchor | pass | 2,256 | 184.7 s |
| `peak_load` | half-open boundary + complexity gate | pass | 2,940 | 241.4 s |
| `clear_days_deadline` | multi-step date rules | pass | 1,593 | 131.8 s |
| `window_mode` | complexity gate + tie-break | pass | 6,994 | 574.9 s |
| **total** | | **4/4** | **13,783** | 1,137.7 s |

| bank | admission standard | incumbent | mean tokens/task |
|---|---|---|---|
| expert (E104) | reference + naive | 7/8 | 9,350 |
| expert2 (E110) | reference + naive | 7/7 | 2,417 |
| **expert3 (E111)** | **reference + naive + SUBTLE** | **4/4** | **3,446** |

### Scoring

| # | prediction | field | outcome |
|---|---|---|---|
| 1 | HEADLINE: not saturated - `passed` <= 3 of 4 | `passed` = 4 | **FALSIFIED** |
| 2 | not impossible - `passed` >= 1 | `passed` = 4 | held |
| 3 | the complexity gate is hardest - `window_mode` NOT `pass` | `pass`, 6,994 tokens | **FALSIFIED** |
| 4 | the plainest task lands - `billing_schedule` IS `pass` | `pass` | held |
| 5 | tasks cost real reasoning - mean tokens > 5,000 | 3,446 | **FALSIFIED** |
| 6 | the harness holds - `no_code` and `transport_failed` both 0 | `outcome_counts` = {pass: 4} | held |

### THE ANSWER

> **The three-arm standard did not work either, and P3 says why.** Every subtle
> arm was proved to fail: the anchor-drift solution, the sweep sorted by time
> alone, the start-normalising deadline, the incremental-count-and-scan mode.
> The model wrote none of them. On `window_mode` it did not merely avoid the
> slow-but-correct answer the subtle arm encodes - it produced a structure that
> clears a gate calibrated to take 15.75 s the plausible way, in 6,994 tokens.
> **A task defined by the wrong answers it defeats is still defined by wrong
> answers.** Naming a better class of wrong answer raised the bar for the arm,
> not for the model.

P5 is the sharper half. The pre-filter said a task the incumbent finishes under
~5,000 tokens is unlikely to discriminate; three of four came in under 3,000 and
the mean fell BELOW expert2's. The tasks are more intricate to specify and no
harder to solve - which is exactly what F150 said about the bank this one was
built to replace, arrived at by a different route.

### Two runs, byte-identical

The first run's results file was destroyed at its last line by an
`IsADirectoryError` - `--out` names a FILE and a directory was passed - so it
was repeated. The repeat is not merely consistent: the per-task token counts are
**identical** (2,256 / 2,940 / 1,593 / 6,994), which is what greedy decoding at
temperature 0 should give and is rarely checked. `run_coding_eval.py` now
refuses a directory `--out` before doing any work rather than after 19 minutes
of GPU time.

### What this does NOT establish

- **It says nothing about whether the bank separates weaker models.** The
  original expert tier gave 7/8 / 4/8 / 1/8 across three quants (E104, F144), so
  a control at ceiling blocks comparison UPWARD and not downward. expert3 was
  not run against a challenger.
- One model, one bank, four items.
- Nothing about code QUALITY - a pass is "passes hidden tests".

### Disposition (owner, 2026-09-06)

**The coding instrument is PARKED**, rather than revised a third time or
repointed at challengers. The remaining GPU time goes to the open
knowledge/harness questions (E112). `expert3` is kept alongside `expert` and
`expert2`: all three are valid, tested, self-contained banks that measure a band
this model is above.

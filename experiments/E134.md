## E134 - E133's attribution is WRONG. Production was already failing R10 before the upgrade. (2026-09-07)

The same four items and the SAME script as E133, run against the gateway's OLD
binary (`067de9371`, build 9865, 3 July) with `-fa on`, no KV quantisation.

| item | old gateway build | expected from control |
|---|---|---|
| R01 | correct | correct |
| R09 | `off_by_calendar` | `off_by_calendar` |
| **R10** | **truncated** | correct |
| R12 | correct | correct |

### The mistake, and what caused it

**Every banked control ran on `b10435` (commit `9e40df63b`, 14 August) - a
sparkbench BENCH build. The gateway's old build was `067de9371`, 3 July, which
is OLDER than the control's.** I treated "the banked control" and "what
production was running" as the same thing. They were never the same thing.

R10 at `-c 16384 -fa on`, `max_tokens 4096`, `reasoning_effort low`:

| build | date | R10 |
|---|---|---|
| `067de9371` | 3 Jul | **truncated** |
| `b10435` / `9e40df63b` | 14 Aug | **correct**, "16 June 2027" |
| `daef7b687` no KV quant | 31 Aug | `off_by_calendar`, "17 June 2027" |
| `daef7b687` + q8_0 KV | 31 Aug | **truncated** |

**R10 is correct on exactly one build and fails on both an older and a newer one,
in different ways.** It is a fragile item, not a regression marker.

### What this retracts

1. **E133's headline - "the runtime turns a correct answer into a wrong one" -
   is withdrawn as stated.** It compared `daef7b687` against a `b10435` control,
   which is a real difference between two BENCH builds, but it is NOT the
   production upgrade `067de9371 -> daef7b687` and was written as though it were.
2. **E132's framing that the upgrade cost R10 is wrong.** The old gateway build
   truncates R10 as well, and with q8_0 KV on top production would have failed it
   before today. **Production did not regress on R10; it was already failing.**
3. The [[F110]] note stands as an observation on `daef7b687` - q8_0 turns a wrong
   answer into no answer there - but it is no longer evidence about what the
   upgrade cost, because the pre-upgrade state was already a truncation.

### What survives

- **The upgrade's verified results are unaffected.** l4 14/15 item-for-item, l3
  12/12, the core bank on both other residents item-for-item, and tool calling -
  all compared like-for-like and all clean (E130, E131, E132).
- **The effort trade is unaffected**: `medium` costs one of fifteen on l4 against
  `low`, measured on one runtime with one variable moving.
- R10 remains the single item this box gets wrong on l5 in production, before and
  after.

### The lesson, stated plainly

**A control is only a control if it ran the configuration you are comparing to.**
Three banked runs agreeing at 23/24 made "the control" feel like an established
fact about the box, and the field naming its binary was in the JSON the whole
time. Checking `server_bin` before building the comparison would have cost one
command; not checking it produced two wrong conclusions and a wrong handoff.

## Incident 2026-09-08 00:56 - deleting the build tree left a binary that could not restart

**Production stayed up throughout and no request failed.** The breakage was
LATENT: the gateway would have failed at its next restart, whenever that came.

### What happened

The owner approved clearing the rollback backups. Removed:
`/opt/sparkrouter/llama.cpp/build-pre-upgrade-20260907-173208` (1.1 GB) and the
`llama.cpp-next` worktree (587 MB).

`llama-server` then failed with `libllama-server-impl.so: cannot open shared
object file` when run from any directory except its own.

### Why

**cmake baked an ABSOLUTE RUNPATH into the new build**, pointing at the tree it
was built in:

```
RUNPATH  /opt/sparkrouter/llama.cpp-next/build/bin:
```

Eight files carried it - the binary and seven libraries. The OLD build used
`$ORIGIN`, which is relative and survives being copied. So `cp -a` moved the
files into place while leaving them resolving their libraries through the
ORIGINAL path, and deleting that path broke them.

**Two things hid it.** The trailing colon in RUNPATH adds the current directory
to the search path, so it still worked when run from its own `bin/`, which is how
every check before the deletion was run. And the running process holds its
libraries mapped, so `/health` returned 200 the whole time.

### The fix, and what it is not

`/opt/sparkrouter/llama.cpp-next/build/bin` recreated as a **symlink** to
`/opt/sparkrouter/llama.cpp/build/bin`, so the stale absolute RUNPATH resolves to
the real libraries. Verified: `llama-server --version` now loads from an
unrelated working directory.

**This is a workaround, not a repair.** The binary still believes its libraries
live in a tree that no longer exists. The repair is either `patchelf --set-rpath
'$ORIGIN'` on the eight files, or a rebuild configured so the installed RUNPATH
is relative. **Patching in place was NOT done deliberately**: the running gateway
has those files mapped, and rewriting a mapped file risks SIGBUS in production.
The safe form is copy, patch the copy, rename over the original - a rename leaves
the running process on its old inode.

### What this cost, and the guard now in place

Net disk reclaimed 1.7 GB, and the rollback is gone - though commit
`067de9371` is still in the clone, so the old build is rebuildable in about
fifteen minutes.

`tools/upgrade_router_llama_binary.sh` now inspects the new binary's RUNPATH
before swapping and warns when it is absolute, naming the consequence and the
`patchelf` fix. A warning rather than a refusal, because the swap itself is
sound; it is the later deletion that is unsafe.

### The lesson

**A check run from the artefact's own directory cannot detect a broken library
path**, because the current directory silently satisfies it. Verify a binary from
somewhere else - which is where a service manager will run it from.

### Incident 2026-09-08 - RESOLVED at 01:04, proven by restart

`tools/fix_router_runpath.sh repair` set RUNPATH to `$ORIGIN` on the binary and
seven libraries by copy-patch-rename, moved the symlink workaround aside, and
restarted the gateway.

Verified independently afterwards: all files report `$ORIGIN`;
`/opt/sparkrouter/llama.cpp-next` no longer exists; `llama-server --version`
loads from an unrelated working directory; the gateway is healthy with four
processes 25 seconds old - **a genuine restart, not a surviving process** - and a
routed request returns content.

**The restart is the proof.** "It starts" was the claim, and only starting it
tests that. Health on a process that was already running would have proven
nothing, which is exactly how the breakage stayed hidden for eight minutes.

Kept for now: `build-runpath-prepatch-20260908-010411` (the pre-patch copies) and
`llama.cpp-next.disabled` (the dead workaround). Both removable.

### A model that disappeared, and did not matter

`/v1/models` listed four entries before the upgrade and three after:
`default` is gone, and `model: "default"` now returns HTTP 400.

**Not a regression.** `ops/router_preset.py` says router mode "ALWAYS PUBLISHES A
MODEL CALLED `default` ... with no model file behind it", treats the name as
RESERVED and refuses to define it. The README names the contract as a gated set
of three - `local_fast`, `local_smart`, `local_code`. `default` was a phantom
with nothing behind it, and the newer build no longer publishes it.

**Raised, checked against the owning project's own source, and dropped.** Worth
recording because the first reading was "a caller could be broken by the
upgrade", and one grep in sparkrouter settled it the other way.

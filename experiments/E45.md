## E45: does Qwen3.8 fix the ONE place the routing guide says the workhorse is unsafe? (2026-08-15, pre-registered before any run)

**Why this exists.** Owner instruction: keep testing other concepts, find its
strength. Every instrument so far has probed the same shape - closed-record
reading and reasoning - and three of them saturated. This probes a different
capability with a **named, measured, reproducible incumbent failure** to aim at.

`reports/2026-07-16-local-model-routing-guide.md` says:

> A tool call whose behaviour depends on a condition -> **Mistral-Small-24B**.
> The Qwen family and gpt-oss apply conditional flags *unconditionally* - 0/5
> on the not-urgent branch. Mistral scored 100% (E33). **This is the one place
> the workhorse is unsafe.**

Qwen3.8 is a Qwen model, so the family prior says it fails. But the defect is
**reasoning inside the tool call**, and reasoning is precisely what this
generation added. If it fixes 0/5, the guide loses its only carve-out and the
model earns a capability the current workhorse does not have. That is a
strength worth looking for, and a clean falsifiable question either way.

**Instrument.** `tools/tooluse_harness_v2.py`, the E33 benchmark, restricted to
its `conditional` category:

| task | what it tests |
|---|---|
| `c1-urgent` | balance EUR 7,400, rule says >5,000 gets URGENT -> URGENT **must** appear |
| `c2-not-urgent` | balance EUR 300, same rule -> URGENT must **not** appear. **This is the 0/5.** |
| `c3-vat` | compute VAT at 23% and a total, put them in the spreadsheet |

`c1` and `c3` are the controls. A model that never writes URGENT passes `c2`
and fails `c1`, so `c2` alone proves nothing.

**Two harness defects fixed before any arm ran, both the same class already hit
four times today.**

1. **`max_tokens` was hard-coded to 1,200.** That is the E33-era value and it
   cannot hold a reasoning trace - Qwen3.8 spends thousands of tokens before
   answering, so a reasoning arm left at 1,200 measures the cap, not the model
   (F20). Now a flag, and **every E45 arm runs at 4,096** including the
   incumbents, so the comparison is internally like-for-like rather than
   inheriting E33's number.
2. **The request timeout was hard-coded to 180s**, which a reasoning model
   blows through. Now derived from `max_tokens`.

**Held FIXED deliberately: `temperature 0.2` and `runs=5`.** Every E33 number
this is measured against used them. They are not oversights and must not be
"improved" to temperature 0 - that would break the like-for-like comparison
the benchmark exists for. Tool use is therefore NOT deterministic here and the
headline is a success RATE over five runs.

**Arms.** All local, b10435, `--jinja`, `-c 32768`, `-np 1`, `max_tokens 4096`,
`runs 5`.

| arm | model | thinking |
|---|---|---|
| A | Qwen3.8-27B-Q4_K_M | `off` |
| B | Qwen3.8-27B-Q4_K_M | `low` |
| C | Qwen3.8-27B-Q4_K_M | `medium` |
| D | Qwen3-30B-A3B-2507 (incumbent workhorse) | n/a |
| E | Mistral-Small-3.1-24B (the 100% reference) | n/a |

D and E are RE-RUN rather than cited from E33: different build (F63), different
date, and now a different token budget.

**Predictions. The FIELD is `success_rate` on the named task, over 5 runs.
Bands are set HIGH on purpose - mine have sat at or below the measured result
five or six times today, and continuing to register low bands would be
repeating a known error rather than learning from it.**

1. **`c2-not-urgent` for the workhorse (arm D): 0.0-0.4.** A reproduction
   check of E33's 0/5. If it now passes, E33's finding has decayed and the
   routing guide's carve-out needs revisiting on its own.
2. **`c2-not-urgent` for Qwen3.8 at `off` (arm A): 0.0-0.6.** With reasoning
   disabled it should behave like the family prior.
3. **`c2-not-urgent` for Qwen3.8 at `low` OR `medium` reaches >= 0.8.** This
   is the discriminating claim and the reason the experiment exists.
4. **Parse rate is 1.0 for every Qwen3.8 arm** - structured `tool_calls`, no
   native format leaked as text. F38 recorded leakage as the Coder's failure,
   not the workhorse's, and Qwen3.8 is not the Coder.
5. **`c1-urgent` and `c3-vat` are >= 0.8 for Qwen3.8 at EVERY level including
   `off`.** These need no conditional reasoning, so if they fail at `off` the
   task is measuring something other than what it claims.

**Falsifier: if `c2-not-urgent` is <= 0.4 for Qwen3.8 at every level, the
conditional-flag defect is architectural to the Qwen family and survived a
generation change.** The routing guide's Mistral carve-out then stands
unchanged and is strengthened by a second generation of evidence, which is a
useful result rather than a null one.

convergence at 100k means the effort level is merely expensive, while
truncation at 100k means `xhigh` does not converge on these tasks at any

than added mid-flight.

### E45 AMENDMENT 1 (declared 2026-08-16 02:30, BEFORE any E45 arm runs)

**The conditional category goes from 3 tasks to 13.** At three tasks one task
was worth 33% of the category score, and E45 exists to decide whether the
routing guide's only carve-out survives. Confirming or overturning a
production routing rule on three tasks is not a measurement, it is a coin
toss with a table around it.

**Every addition is a PAIR** - one branch where the condition holds and one
where it does not. This is the whole design: a model that applies the flag
unconditionally passes the true branch and fails the false one, which is
exactly the defect E33 recorded. An unpaired task cannot distinguish that
failure from competence, which is why the original `c1`/`c2` were already a
pair and why every new one is too.

| pair | condition shape | false branch |
|---|---|---|
| c4 / c5 | a date before a threshold | c5 |
| c6 / c7 | a category read from a looked-up record | c7 |
| c8 / c9 | **whether to call a tool at all** | **c9** |
| c10 / c11 | a compound AND of two facts | c11 |
| c12 / c13 | a threshold on a figure it must compute first | c12 |

**c8/c9 is a new SHAPE, not just a new instance.** Every pre-existing
conditional task tests a flag inside a call that was always going to happen.
c9 tests whether the model declines to send an email at all when the condition
fails. In production that is the higher-stakes version - a wrongly-set title is
an edit, a wrongly-sent client email is not retractable.

**Marker words were chosen against substring collision.** EXPEDITED/ROUTINE
and URGENT/STANDARD share no substring, so a check for one cannot fire on the
other. Numeric markers were avoided where a word would do, because a number
can appear inside an unrelated figure or a date and score a hit the model did
not earn. This is the m11 key lesson applied to tool arguments.

**The graders are validated, not assumed.**
`tools/validate_tooluse_conditional.py` runs 20 synthetic respondents, each
built to trigger exactly one verdict - including the E33 defect itself and the
dangerous c9 branch - and exits non-zero if any check cannot tell a compliant
answer from its named failure. **20/20 pass.** An unvalidated grader reports a
number nobody can trust.

**Predictions 1-5 stand EXACTLY as registered.** They name `c1`, `c2` and `c3`
individually and are unaffected by tasks being added around them. Two new
predictions cover the new material, and no existing band is rewritten:

6. **The five FALSE branches as a group (c5, c7, c9, c11, c12), mean
   `success_rate`:** workhorse **0.0-0.5**; Qwen3.8 at `low` or `medium`
   **>= 0.7**. This is the generalised version of the c2 claim - if the fix is
   real it should hold across condition shapes, not just on the one branch E33
   happened to test.
7. **`c9-select-no-email` specifically, for every arm.** Registered separately
   because it is the only task where failure sends a real client
   communication, and because conditional tool SELECTION has never been
   measured on this box at all. **No band is registered for it** - there is no
   prior to set one from, and inventing a band for a shape nobody has measured
   would be the F65 error in a new place.

**Cost.** 13 tasks x 5 runs x 5 arms = 325 task-runs against the original 75.
The queue script needs no change: it selects by category, so the expanded set
is picked up automatically.

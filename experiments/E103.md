## E103 PRE-REGISTRATION - is ThinkingCap-Qwen3.6-27B a better `smart` slot than our incumbent? (2026-09-04)

### Why this experiment exists

| | |
|---|---|
| **which success question** | production serving - this is a same-footprint drop-in for the `smart` slot |
| **uncertainty reduced** | whether a different base model at the same size and quant does the knowledge work better AND terminates more reliably |
| **decision that changes** | whether `tools/e94/models-asym.ini`'s `smart` entry should be proposed for change to sparkrouter |

### Provenance of the hypothesis

The same community report behind E101 ranks `ThinkingCap-Qwen3.6-27B-Q4_K_M-MTP`
**first of nine** builds tried, above every Qwen3.8-27B quant, for "everyday
tasks and long agentic work", citing less looping and less wasted deliberation.
Reported on an RTX 3090 Ti / Windows box at 50-65 tok/s. **The throughput figure
does not transfer to this hardware and is not tested.** What is tested is the
capability and termination claim, on our bank, against our incumbent.

### The pair

| | incumbent | challenger |
|---|---|---|
| file | `Qwen3.8-27B-Q4_K_M.gguf` | `ThinkingCap-Qwen3.6-27B-Q4_K_M-MTP.gguf` |
| bytes | 16,810,714,336 | 16,810,713,408 |
| requantiser | - | protoLabsAI (third-party requant of bottlecapai's release) |

A 928-byte difference, which is metadata string length rather than tensors.
**Same footprint, so this is a model comparison and not a size/quality trade.**

### PROBED BEFORE ANY PREDICTION WAS WRITTEN (F124), and it reshaped the design

| fact | value | how obtained |
|---|---|---|
| sha256 | matches pinned LFS oid `0ba445d2...` | `fetch_hf_model.sh` on arrival |
| `general.architecture` | `qwen35` - **same as our incumbent** | GGUF header |
| `n_ctx_train` | 262,144 - **same as our incumbent** | GGUF header |
| `general.base_model.0` | **`Qwen/Qwen3.6-27B`** | GGUF header |
| `general.tags` | `token-efficient`, `efficient-thinking` | GGUF header |
| **`reasoning_effort` in chat template** | **ABSENT - 0 occurrences** | full template dump |

Two of these change the experiment.

**1. It is a different BASE MODEL, not a requant of ours.** Same architecture
family (`qwen35`) and identical tensor shapes - which is why the file lands 928
bytes from our incumbent at the same quant - but it declares `Qwen/Qwen3.6-27B`
as its base against our Qwen3.8-27B. The near-identical size is architecture,
not lineage, and reading it as "the same weights renamed" would have been wrong.

**2. It has NO graded reasoning control, and that kills effort-matching.** Our
incumbent's template resolves `reasoning_effort` through `low`/`medium`/`xhigh`
(6 occurrences, `xhigh` 5, `medium` 2). ThinkingCap's has **zero**, carrying
only a binary `enable_thinking`. **Passing `--thinking low` to it would be
silently dropped** - the arm would run at its default while the result file
recorded `"thinking": "low"`, and the comparison would be a lie the output
format could not expose. This is F128's shape exactly, and it is why the probe
happened before the predictions rather than after a puzzling result.

**Consequence, stated rather than averaged away: the two arms are NOT
effort-matched, and cannot be.** Each model runs at the configuration it would
actually be SERVED at - our incumbent at the setting F71 established
(`medium`), ThinkingCap at its own default. That is the honest comparison for
the decision at hand ("should the `smart` slot change?") and it is NOT a
controlled comparison of the two model families. No claim below is a claim
about Qwen3.6 versus Qwen3.8 as such.

**A third fact, recorded because it bears on E101 rather than E103.** BOTH
GGUFs carry embedded sampling defaults: `general.sampling.temp = 1.0`,
`top_k = 20`, `top_p = 0.95`. That is precisely the config the community report
uses - so those settings are the models' own published recommendations, not
something the reporter invented. **Every eval in this repo, and production,
runs at `temperature 0`, overriding them.** E101 is therefore measuring the
gap between how these models are shipped and how we serve them.

### The two arms

| arm | instrument | config | comparator |
|---|---|---|---|
| **A capability** | `run_ps_eval.py --tier l5`, 24 items | `-c 16384`, `--server-extra '-fa on'`, model default effort | the E102 incumbent run, same session, same quiet GPU |
| **B termination + efficiency** | `run_coding_eval.py --task-set core --only <the six E101 tasks>`, greedy | `-c 16384`, `--max-tokens 8192`, no `-fa` (matching E101 Amendment 1) | **E101 cell 1** - same six tasks, same greedy payload, same build |

Arm B is greedy so it compares against a banked cell rather than a fresh one.
The sampled looping question was answered for the incumbent in E101 and is not
re-opened here.

**Before either arm: an inertness control.** Send one prompt to ThinkingCap with
`reasoning_effort: low` and one with nothing, and compare completion tokens. The
template says the parameter is absent; the control proves the SERVER drops it
rather than erroring or partially honouring it. **Equal token counts confirm
inertness - they do not mean the model is efficient.** If the request instead
FAILS, that is a different fact and arm A's config changes.

### Predictions, each naming the FIELD it is scored against

| # | prediction | scored against |
|---|---|---|
| 0 | `reasoning_effort` is inert on this model | control: completion tokens with `low` vs with nothing differ by **< 5%**, and neither request errors |
| 1 | the challenger is competitive on evidence work | challenger `band E correct` **>= 10** of 12 |
| 2 | **DISCRIMINATING: it does NOT beat the incumbent on reasoning** | challenger `band R correct` minus E102 incumbent `band R correct` **<= 0** |
| 3 | the report's termination claim shows up | challenger arm-B `truncated` **<=** E101 cell 1's `truncated` (which was **0**) |
| 4 | **the token-efficiency claim is real** | challenger arm-B total `completion_tokens` **< 11,194** - the sum E101 cell 1 spent on the same six tasks |
| 5 | it produces parseable code | arm B `no_code` **= 0** of 6 |
| 6 | the graders hold | arm A `format_error` **= 0** across 24 |

**P3 is a hard prediction to pass and is registered knowing that.** E101 cell 1
truncated **zero** of six, so the challenger can only tie, never win. That is
stated now rather than discovered later: on this instrument the termination
claim has no room to show a benefit, and P4 - tokens spent - is where a
token-efficiency finetune can actually demonstrate something.

P2 keeps the unflattering direction. The incumbent scores **11/12** on band R
(E78), close to the ceiling.

### Registered decision rule

| observed | action |
|---|---|
| P0 FAILS (the parameter is not inert) | STOP. The probe's reading of the template is wrong, and every config assumption in this entry is re-derived before any arm runs |
| P2 FALSIFIED (challenger beats band R) | a real result. Re-run BOTH arms with fresh seeds before any recommendation - one 24-item bank does not move production |
| P2 holds and P1 holds and P4 holds | **comparable capability for fewer tokens.** That is a genuine reason to consider the swap even without a capability win, and it is reported as an efficiency result, not a quality one |
| P2 holds and P4 FAILS | no capability win and no efficiency win. Report "no reason to switch" plainly |
| P1 fails (band E < 10) | the challenger is worse at evidence work; report the community ranking as NOT REPRODUCED on this bank and stop |
| the model does not load | that is the finding. Report it; do not manufacture a capability number |

### What this cannot establish

- **One bank, 24 items, one run per arm.** No claim of superiority survives that alone.
- **The arms are not effort-matched and cannot be**, for the reason above. Any
  difference measured here includes that asymmetry and is not attributable to
  the weights alone.
- **A third-party requant.** Any finding names protoLabsAI, because the MTP head is theirs.
- **Nothing about their box or their 50-65 tok/s.** Different GPU, OS and build.


## E103 RESULT - ThinkingCap is a better DEFAULT and a worse CEILING; the efficiency claim inverts on what you compare against. PREDICTION 4 FALSIFIED. (2026-09-04)

Two arms plus a control, quiet GPU, build `b10435`. **The arms are NOT
effort-matched and cannot be** (the model has no graded reasoning control); each
ran at the configuration it would actually be served at.

### Arm A - L5 capability

| arm | total | band R | band E | miss | median/item |
|---|---|---|---|---|---|
| incumbent (E102) | 23/24 | 11/12 | 12/12 | `R09` | 40.93s |
| GSQ-RCO IQ3_S (E102) | 23/24 | 11/12 | 12/12 | `R09` | 26.90s |
| **ThinkingCap-Qwen3.6-27B** | **23/24** | **11/12** | **12/12** | **`R09`** | **78.12s** |

**Three models, zero separation, the same failing item.** This is the E102 null
repeated against a different BASE MODEL, and together the two results retire the
bank for model comparison - recorded as F142.

### Arm B - the token-efficiency claim, and why its sign depends on the comparator

Six coding tasks, greedy, same payload as E101 cell 1.

| config | pass | tokens |
|---|---|---|
| incumbent at `medium` (TUNED, F71's line) | 6/6 | **11,194** |
| **ThinkingCap at its own default** | **6/6** | **20,437** |
| incumbent at its own default (`xhigh`, sampled, E101 c4) | 7/18 | **36,515** per run |

**Against our TUNED incumbent, ThinkingCap costs 83% more tokens for the same
perfect score - P4 FALSIFIED. Against our incumbent's own DEFAULT, it costs 44%
fewer and passes 6/6 against 39%.**

Both statements are true and they are about different questions. The
`efficient-thinking` tag is earned: **ThinkingCap does not need an effort dial
because its default is already sane; ours needs one and fails badly without it.**
A user who never finds `reasoning_effort: medium` would rank ThinkingCap far
above Qwen3.8-27B - which is exactly what the community report does, and it is
defensible from that starting point.

⚠️ **The third row is not a clean comparator**: E101 cell 4 is SAMPLED
(temp 1.0) where arm B is greedy. A greedy-at-`xhigh` incumbent cell was never
run. The 36,515 figure carries a sampling difference and is quoted as
directional, not as a matched arm.

### P0's control was degenerate, and the pass is withdrawn as EVIDENCE

The control reported `relative difference 0.000%` from `completion_tokens`
2048 vs 2048 - with `finish_reason=length` on **both**. Two generations that hit
the cap have equal token counts **by construction**, so the comparison could not
have detected an effect had there been one. It is an equality test over a
saturated measure, the same shape as E101's C1 passing on two identical
3-character failures earlier the same day.

**The design decision does not depend on it and stands**: the chat template
carries ZERO occurrences of `reasoning_effort` against the incumbent's six, and
that evidence is independent. What is withdrawn is the claim that P0 PROVED it.
`tools/e103_p0_control.py` now detects the saturated case and falls back to
byte-comparing the generated text.

✅ **CORRECTED RE-RUN DONE (2026-09-05 04:33, quiet GPU, E104 having finished at
04:32:26).** Both generations terminated NORMALLY this time - `finish=stop` at
**4,202 completion tokens each**, not truncated by any cap - and the counts are
identical to 0.000%. At temperature 0 that is a real equality on a measure that
was free to differ. **P0 now HOLDS on evidence that could have falsified it**,
and the design decision it supports (each model at its own default; arms
declared not effort-matched) is confirmed rather than merely unrefuted.
Evidence: `results/raw/e103/p0-control-CORRECTED.txt`.

### The recommendation

**Do NOT swap the `smart` slot to ThinkingCap.** At the configuration we
actually serve, our incumbent does the same work for 45% of the tokens, and
ThinkingCap has no effort control with which to close that gap. It was also the
slowest of the three arms on arm A. It is a better model to hand someone who
will not tune it - which is not our situation.

### What is NOT claimed

- **The arms are not effort-matched.** Every number here includes that asymmetry.
- **Arm A measured nothing**, because the bank is saturated (F142). "Matches the
  incumbent on capability" is a statement about the ruler.
- **A third-party requant** (protoLabsAI, of bottlecapai's release); the MTP head
  is theirs and was not enabled.
- **Nothing about their box, OS, build, or their reported 50-65 tok/s.**

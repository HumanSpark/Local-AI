## E59: is MTP speculative decoding OUTPUT-PRESERVING on this model? (2026-08-19, pre-registered before any run)

**Why now.** Qwen3.8-27B was trained with multi-step Multi-Token Prediction, and
this box has been loading those weights and discarding them. From the E57 27B
serverlog, unprompted:

```
W model has unused tensor blk.64.nextn.eh_proj.weight (size = 29491200 bytes) -- ignoring
W model has unused tensor blk.64.nextn.enorm.weight  (size = 20480 bytes) -- ignoring
```

`/opt/models/staging/Qwen3.8-27B-Q4_K_M.gguf` retains the `blk.64.nextn.*` MTP
layers, and llama.cpp build 770 (`9e40df63b`) supports `--spec-type` with
`draft-mtp` among its values. **No run in this repo has ever passed it**, so
every published Qwen3.8 figure was measured with a draft head resident and idle.

**And a named reason to distrust it.** A current llama.cpp Qwen3.8 investigation
reports strong MTP throughput *alongside deterministic-output divergence still
under investigation*. Speculative decoding is supposed to be mathematically
exact - the draft is verified against the target, so accepted tokens are the
tokens the target would have produced. If output moves, either the
implementation is not exact on this model or the acceptance path is wrong. That
is a correctness question, and a score cannot answer it: two runs can both be
13/13 while disagreeing on every word.

### The probe is E57's determinism result, which is why this is worth running now

E57's 27B produced **ten of ten byte-identical answers across two separate runs
and two separate server processes**, asked at turn 3 in one order and turn 16 in
the other. That is a measured noise floor of **zero**, and it makes this model an
unusually sensitive detector: re-run the identical conversation with one flag
changed and any divergence is attributable to the flag.

**Design: one variable.** E57's 27B arms ran `server_extra=''`. The MTP arms run
`server_extra='--spec-type draft-mtp'` and nothing else - same model, same
`-c 32768`, same `-np 1`, same `max_tokens 5120`, same `reasoning_effort: low`,
same conversation scripts, same grader. `tools/diff_run_answers.py` refuses the
comparison unless model, conversation, ctx, max_tokens and thinking all match
and only `server_extra` differs.

Both orders are run, so the comparison is **26 graded cells**, and it re-tests
E57's cross-run byte-identity property under the new config as well as against
the old one.

### Predictions (registered before any arm runs)

1. **PRIMARY: all 26 answer strings are byte-identical to their non-MTP
   counterparts.** This is what "speculative decoding is exact" means. It is
   registered as the expected result rather than the hoped-for one, because the
   alternative is a correctness defect and should be loud.
2. **`correct` is 13/13 on both MTP arms**, matching E57 exactly.
3. **Wall time improves by at least 1.2x on both arms.** MTP with a resident
   draft head should win something on a decode-heavy workload; below 1.2x it is
   not worth a serving-config change and the acceptance rate is the thing to
   look at next.
4. **The `unused tensor ... ignoring` warnings disappear from the serverlog.**
   This is the mechanical check that the flag did anything at all - without it a
   "no change" result could simply mean MTP never engaged, which would look
   identical to "MTP is exact" on every other measure.
5. **The `recent` probes stay 3/3 on both arms.**

**Falsifier: if ANY answer string differs**, MTP is not output-preserving on this
model at this build, the throughput number is irrelevant, and `--spec-type
draft-mtp` must not go near `serving.conf`. Report the divergence, not the speed.

**Second falsifier, on the instrument: if the `unused tensor` warnings persist**,
the flag did not engage and this experiment measured nothing - a null result here
would be an artefact, not a finding.

**Cost.** 2 runs x 18 turns on the 27B, local, no cloud spend. E57's arms took
695.9s and 565.3s, so roughly 20 minutes plus whatever MTP changes.

### E59 AMENDMENT 1 (2026-08-19, declared BEFORE any E59 arm ran)

New evidence arrived between pre-registration and the first run, so it is
declared here rather than used to explain a result afterwards.

**Two upstream llama.cpp issues, both bearing directly on prediction 1:**

- **#25618** - draft-model speculative decoding, `draft-mtp` and `draft-dspark`
  included, **changes greedy output on QUANTIZED target models**, reproduced on
  **Strix Halo with Vulkan**. Our target is `Qwen3.8-27B-Q4_K_M` and our backend
  is Vulkan/RADV on gfx1151. That is our exact configuration.
- **#27151** - a Qwen3.8 report of MTP draft acceptance collapsing to **1 of 633**.

**Prediction 1 was registered as "all 26 answer strings byte-identical", on the
principle that speculative decoding is mathematically exact. The evidence above
says that principle does not hold in this implementation on quantized targets.
I now expect prediction 1 to be FALSIFIED**, and I am saying so before the run
rather than claiming afterwards that I knew. The prediction stands as
registered; what changes is my stated expectation of it, and the falsifier
becomes the likely outcome rather than the alarm.

**This makes the run MORE worth doing, not less.** If divergence is real on our
config, we will have measured it on an instrument with a zero noise floor, which
almost nobody has. If it is absent, that is a genuine surprise worth reporting.

**A third possibility the acceptance bug forces us to name:** MTP engages,
accepts almost nothing, output is byte-identical, and wall time is unchanged or
worse. That would satisfy predictions 1 and 2 while meaning nothing at all -
so **MTP acceptance must be recorded, not inferred from the wall time.**
Prediction 4 (the `unused tensor` warnings disappearing) proves the flag
engaged; it does not prove the draft was ever accepted.

### E59 DESIGN REVISION (same amendment): two settings, chat tier separated

The owner's framing sharpens the question from "is MTP exact" to **"can
Qwen3.8-27B + Vulkan + MTP make the 91.3% chat tier fast enough that routing
becomes unnecessary?"** Same-hardware reports put MTP at roughly **12.5 -> 24.1
tok/s** on Q4 under Vulkan on an EVO-X2, which is large enough to move E58's
2-second falsifier. So the design splits:

**Stage 1 - the correctness gate, and it is a GATE.** E57's `heldout-ab`
conversation re-run at `--spec-draft-n-max` **2** and **4**, each diffed against
the vanilla `ab` run cell by cell. 13 graded cells per setting.

> **MTP graduates only if the 27B stays 13/13 AND every answer string is
> unchanged.** The 27B is interesting *because* it is extraordinarily reliable
> in these instruments. Trading that away to make it resemble the workhorse
> defeats the purpose of serving it at all.

If a setting passes, its mirror `heldout-ba` run confirms the cross-run
byte-identity property. If MTP-2 passes and MTP-4 does not, MTP-2 is the
operating point. If neither passes, `--spec-type draft-mtp` does not go near
`serving.conf` and the two-model architecture stands.

**Stage 2 - chat-tier latency only**, and only for settings that passed stage 1.
Three arms (none / MTP-2 / MTP-4) on the chat prompts alone, capturing **warm
median, p95, generated tokens and MTP acceptance**. Not another 48-request
instrument: E57 supplies the quality probe and the traffic log already named the
tier that decides it.

**Deliberately postponed:** `n=6`, `n=12`, stacked n-gram speculation, quant
sweeps and any HIP build. Upstream MTP correctness and acceptance are actively
buggy, so the question is whether n=2 or n=4 *already* changes the architectural
decision. **HIP specifically is dropped rather than deferred** - same-hardware
evidence suggests Vulkan can be the better speculative-decoding backend on
Strix Halo even where ROCm wins elsewhere, so "we are on Vulkan" is recorded as
a fact about our figures, not treated as a defect to fix.

now queued rather than folded in.

## E59 STAGE 1 RESULT (2026-08-19): MTP passes the correctness gate, and spends the determinism property to do it

| arm | correct | answer strings identical | **strict** identical | wall | decode |
|---|---|---|---|---|---|
| vanilla | 13/13 | - | - | 695.9s | 10.87 tok/s |
| MTP n=2 | 13/13 | **13/13** | 5/13 | 407.6s (1.71x) | 19.21 (**1.77x**) |
| **MTP n=4** | 13/13 | **13/13** | **10/13** | 376.9s (1.85x) | 22.65 (**2.08x**) |

**n=4 is better on every axis at once** - faster AND more deterministic - so n=2
is dropped from stage 2. Acceptance falls from 93.2% to 83.4%, but accepted
drafts per verification rise 1.86 -> 3.34 (effective 2.86 -> 4.34 tokens per
verification), and the extra accepted span more than pays for the lower rate.
Draft length was **not clamped**: n=4 genuinely offered 4-token drafts from a
model with `nextn_predict_layers = 1`, because llama.cpp's MTP drafter feeds the
single NextN mechanism forward until `n_max`.

**Prediction 1 HELD and AMENDMENT 1's expectation was WRONG.** The amendment,
written before the run on the strength of upstream #25618, said I expected all-
identical answers to be falsified. All 13 answer strings are identical on both
arms. #27151's acceptance collapse also did not reproduce - 83-93% here, in line
with #26750's ~91-92% on RADV/Vulkan.

**But #25618 is real, and it lands where a score cannot see it.** The full
completions moved on **8 of 13** cells at n=2 and **3 of 13** at n=4. The sharp
one is `F1`: **2,201 -> 1,289 generated tokens at n=2**, same final answer. That
is a different reasoning path reaching the same conclusion, not noise.

So the honest verdict is two claims and they must not be collapsed:

- **The graded result survives.** By the gate as registered - 13/13 AND every
  answer string unchanged - **MTP graduates, with n=4 the operating point.**
- **E57's determinism property does not.** We can no longer say this model
  reproduces byte-identically under this config. The `strict_identical` check
  was added before results were seen and measures something the registered gate
  did not ask about, so it is reported beside the verdict rather than folded
  into it. The gate is not moved in either direction.

**A deployment concern the speed figure hides:** at n=2, `F1` used 41% fewer
tokens for the same answer. If that generalises, part of MTP's benefit is
SHORTER REASONING rather than faster tokens - a quality change wearing a
performance costume. Stage 2 measures token count explicitly for that reason.

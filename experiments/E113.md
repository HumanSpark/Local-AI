## E113 PRE-REGISTRATION - the repaired aider task set, actually run (2026-09-06)

**Registered before the run.** `results/raw/e113` does not exist.

### Why this experiment exists

E109 arm A scored **0/3** on `tools/aider-tasks.json`. Two of those three were
`invalid-precondition`: the work they described had been done and committed, so
their `verify` passed BEFORE the model ran and `classify()` correctly refused to
score them. Only T1 was a genuine fail.

A 0/3 with no measurement behind it reads as a broken harness. The seeds were
repaired on 2026-09-06 - T2's now removes the tracked implementation, T3's
restores the two pre-fix blobs by sha - and
`aider_task_runner.py --check-preconditions` reports all three valid (rc 1, 2, 1).

**A repair with no run is an unfinished repair.** This is the measurement that
replaces the 0/3.

| | |
|---|---|
| **which success question** | whether the incumbent, through Aider, completes real repo-level tasks |
| **uncertainty reduced** | what the 0/3 should actually have been |
| **decision that changes** | whether repo-level agentic work is a usable instrument here at all |

### Design

`Qwen3.8-27B-Q4_K_M`, build `b10435`, quiet GPU, served on 8400 with the same
near-reproduction of the production flags E112 states and for the same reason
(the live `serving.conf` is unreadable by `bench`). Aider reaches it
through `tools/aider_probe.py` on 8499 so first-turn latency and token counts
are recorded. Per-task cap 1,800 s. Each task runs in a fresh disposable
worktree, seeded, verified before and after.

**The run refuses to start unless `--check-preconditions` passes.** That gate is
the direct lesson of E109 arm A.

### Registered decision rule

| observed | action |
|---|---|
| >= 1 pass, 0 invalid | the bank is repaired and measuring. Record the score; it replaces the 0/3 |
| 0 pass, 0 invalid | a real result, not a fault. Report 0/3 as MEASURED and say what failed |
| any `invalid-precondition` | the repair is incomplete despite the pre-check. Fix the seed before believing any score |
| any `timeout` | recorded as its own outcome, never folded into fail - a task that never completed was not attempted to completion |

### What replaces the 0/3

E109 arm A's 0/3 was two rotted preconditions and one genuine fail. Measured
properly the same three tasks give **2/3**, and T1 - the one task E109 actually
scored, as a fail - **passes here in 73 seconds on a single request**. That
difference is not attributed: E109's arm ran against a different serving config
on a contended GPU, and this run changed both.

### T3, and why "fail" is the honest label but not the whole story

The verify is unambiguous: `tests/test_kokoro_gateway.py:14` still executes
`from fastapi.testclient import TestClient` at module level, collection aborts
with 2 errors, gate 1 fails.

But the edit Aider's log shows the model PROPOSING is correct in shape - add
`import pytest`, call `pytest.importorskip("fastapi", ...)` before the
`TestClient` import, keep every test. The same log shows the edit being applied
reaching **`26 / 56 lines [46%]`**, and the second turn spent its entire output
reasoning about which files were in the chat rather than correcting anything.
Aider then exited **0**.

**The leading explanation is an incompletely applied whole-file edit, and it is
NOT proven here**, because the evidence that would settle it was destroyed by
the instrument (below). What IS established: the model's proposed change was
sound, the file on disk was not, and the harness reported success.

### The instrument defect this run exposed, now fixed

`aider_task_runner.py` wrote `aider-run.log` INTO the worktree before capturing
`git diff`, and capped the diff at 20,000 characters. So the run log - 527 lines
of repo-map warnings - crowded the task's own change out of the record entirely.
**The field that exists to explain a failure contained no part of the failure.**

Three changes, all in this run's instrument rather than its subject:

1. `git diff` now excludes the Aider artefacts by pathspec, not only
   `files_touched`.
2. A clipped diff records `diff_truncated_chars` rather than looking complete.
3. `final_files` captures the end state of every file the task was allowed to
   edit, so attribution survives the disposable worktree.

T3's exact final file is therefore **not recoverable for this run**, and that is
stated rather than inferred around.

### What this does NOT establish

- Three tasks, one model, one harness, one run.
- **Not a harness comparison.** Hermes is not an arm; E109's Hermes numbers were
  measured against the unrepaired set.
- Nothing about code quality beyond each task's own `verify`.
- The serving config is the same near-reproduction E112 states, for the same
  reason.

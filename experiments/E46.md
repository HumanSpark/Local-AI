## E46: does `-c` break temperature-0 determinism? (2026-08-16, pre-registered before any run)

**Why this exists.** E44 arm A and E43 arm B put **byte-identical prompts** to
the same model at the same effort and temperature 0, and got **different
answers**:

| matter | E43 arm B | E44 arm A | delta | prompt_tokens | answer identical? |
|---|---|---|---|---|---|
| m11-limitation-clocks | 8,046 | 8,696 | +8.1% | 668 = 668 | **NO** |
| m12-liability-cap-basis | 3,222 | 3,950 | +22.6% | 755 = 755 | **NO** |
| m13-interest-two-clocks | 6,686 | 7,441 | +11.3% | 711 = 711 | **NO** |

Same model file, same b10435 build, same `thinking=xhigh`, same
`temperature 0`, same `-np 1`, identical `prompt_tokens` on every matter -
which proves the same bytes reached the model. **F59 says local arms are
deterministic at temperature 0. On this evidence that is not unconditionally
true.**

**Exactly two variables differ**, and neither run came within 3x of either
cap:

| | E43 arm B | E44 arm A |
|---|---|---|
| `-c` | 32,768 | 131,072 |
| `max_tokens` | 24,576 | 100,000 |

**This must be ISOLATED, not attributed.** Earlier today an apparent
determinism failure between E41 n=0 and E42 know-low turned out to be eleven
rescoped questions - a ruler error, not a model result - and the reflex to
explain rather than isolate is exactly what produced it. Two variables changed
here, so no cause is claimed until one is held still.

**Why `-c` is the plausible suspect and `max_tokens` is not.** `max_tokens` is
a stop condition; at temperature 0, generation up to the cap should be
unaffected by where the cap sits, and neither run approached it. `-c` changes
KV cache allocation - on this DeltaNet hybrid, 2,048 MiB at 32,768 against
8,192 MiB at 131,072 - and a different allocation can change
floating-point reduction order, which changes logits, which changes the
argmax wherever two candidates are close. That is a mechanism; it is not yet
evidence.

**Design. One matter (m12, the cheapest at ~3,200 tokens), three cells,
`thinking=xhigh`, temperature 0.**

| cell | `-c` | `max_tokens` | isolates |
|---|---|---|---|
| 1 | 32,768 | 24,576 | **control** - must reproduce E43 arm B |
| 2 | 131,072 | 24,576 | `-c` alone |
| 3 | 32,768 | 100,000 | `max_tokens` alone |

**Comparison is BYTE EQUALITY of the answer string**, not token count and not
score. A token count can match while the text differs; the direct comparison
is available here, so a proxy would be the wrong instrument (this is
`development-discipline.md`'s compare-like-for-like rule).

**Predictions.**

1. **Cell 1 is byte-identical to E43 arm B's m12 answer.** This is the control
   and it carries the experiment: if it FAILS, the model is not deterministic
   at a fixed config at all, F59 is wrong outright rather than
   over-generalised, and every single-run result in this repository becomes a
   sample rather than a measurement. That would be the most consequential
   finding of the programme and it would invalidate more than it explains.
2. **Cell 2 differs from cell 1.** `-c` is the cause.
3. **Cell 3 is byte-identical to cell 1.** `max_tokens` is not the cause.

**If predictions 2 and 3 both hold, F59 needs an amendment reading: local
arms are deterministic at temperature 0 FOR A FIXED `-c`, and any comparison
across different `-c` values is not byte-comparable.** That would put a
caveat on cross-config comparisons throughout this repository, including
E41's scale sweep - which is internally safe, because every arm there ran at
`-c 32768`.

**Falsifier for the whole experiment: if all three cells are byte-identical to
each other and to E43 arm B, the divergence came from something not yet
identified**, and the honest report is that a reproducible difference exists
whose cause has not been found. It would not be attributed to `-c` on the
strength of a mechanism story.

### E46 AMENDMENT 1 (declared 2026-08-16 03:15, BEFORE any E46 cell runs)

**E44 arm B arrived and answered predictions 2 and 3 before E46 could run.
Both were WRONG, and the experiment is redirected rather than run to confirm a
hypothesis the data has already killed.**

| run | `-c` | `max_tokens` | m11 | m12 | m13 |
|---|---|---|---|---|---|
| E43 arm B | 32,768 | 24,576 | 8,046 | 3,222 | 6,686 |
| E44 arm A | 131,072 | 100,000 | 8,696 | 3,950 | 7,441 |
| E44 arm B | 262,144 | 200,000 | **8,696** | **3,950** | **7,441** |

**E44 arms A and B are BYTE-IDENTICAL on all three answers** while `-c`
doubled and `max_tokens` doubled. If `-c` were the cause, 131,072 -> 262,144
would have diverged. If `max_tokens` were the cause, 100,000 -> 200,000 would
have. Neither did. **Prediction 2 (`-c` is the cause) and prediction 3 are
both refuted by data collected before the experiment started.** The registered
mechanism story about KV allocation changing reduction order was plausible,
tidy, and wrong.

Rope was also checked and ruled out directly rather than assumed: all three
runs report `rope scaling = linear`, `freq_scale_train = 1`,
`n_ctx_orig_yarn = 262144`. There is no context-dependent rope scaling to
blame.

**The real variable was in the runs all along: REQUEST SEQUENCE POSITION.** In
E43 these matters were requests **11, 12 and 13** of thirteen. In E44 they were
requests **1, 2 and 3**. The server log shows why that matters:

```
slot operator(): restored context checkpoint (pos_min = 41, pos_max = 41,
                 n_tokens = 42, n_past = 42, size = 149.626 MiB)
```

and the prompt-eval counts differ for the same prompt: m11 evaluated **618**
tokens in E43 against **668** in E44, because E43 reused 50 more tokens of
cached prefix from the request before it. llama-server reuses KV cache across
requests, so **an answer depends on what ran before it in the same server
session.** Once m11 diverges, m12 and m13 inherit a different cache state.

**This is consistent with every data point, which the `-c` story was not:**
same sequence and different config gives identical output (arms A vs B);
different sequence gives different output (E43 vs E44).

**Redesigned cells. One variable - sequence position - at E43's exact config
(`-c 32768`, `max_tokens 24576`, `thinking=xhigh`).**

| cell | matters run | m12 is request | tests |
|---|---|---|---|
| 1 | m12 alone | 1st | baseline |
| 2 | m11, m12, m13 | 2nd | does position alone change the answer |
| 3 | all 13 | 12th | **must byte-reproduce E43 arm B** |

**Cell 3 is the control that now carries the experiment.** Identical config
AND identical sequence must give an identical answer. If it does, determinism
holds for a fixed (config + request history) and F59 needs only a scope note.
If it does NOT, the model is not reproducible run to run and every single-run
number in this repository is a sample, which would be far more consequential.

**Revised predictions.**

1. **Cell 3's m12 answer is byte-identical to E43 arm B's m12.** The control.
2. **Cell 1's m12 differs from cell 3's m12.** Sequence position is the cause.
3. **Cell 2's m12 differs from cell 1's** and may or may not match cell 3 -
   no band registered, because whether two prior requests reproduce the cache
   state of eleven is not something any evidence here constrains, and
   inventing a band for it would be the F65 error again.

**Scope if this holds.** It does NOT invalidate any score in this repository.
Every comparison made so far ran its arms with the same request sequence -
E43's four arms each ran the same 13 matters in the same order, E41's sweep
ran the same 12 questions - so all within-experiment comparisons remain
like-for-like. What it forbids is comparing a single item's answer ACROSS runs
with different request histories, which is exactly the comparison that raised
the question.

### E44 arm C, partial: `normalize_path` answers the whole experiment

**The single most decisive result of the budget probe, recorded before arm C
finishes because it settles the question the owner asked.**

| run | budget | outcome | tokens | seconds |
|---|---|---|---|---|
| E33 original | 8,192 | truncated | 8,192 | - |
| E33 RE-RUN 2 | 24,576 | truncated | 24,576 | 2,080.9 |
| **E44 arm C1** | **100,000** | **`no_code`** | **51,845** | **4,603.9** |

**Given twelve times the budget it originally capped at, it did NOT truncate.
It generated 51,845 tokens over 77 minutes, stopped of its own accord, and
produced no code at all.**

**The two earlier truncations were masking this, not causing it.** For two runs
the diagnosis was "the budget is too small" and the fix was to raise it. Raise
it far enough and the real behaviour appears: on this task at `xhigh` the model
does not converge. It was never one cap away from an answer.

E44's registration anticipated this exact outcome and named it a result rather
than a failure:

> If the toughest matters produce 100,000 tokens of reasoning and no answer,
> that is the finding - it says maximum effort on this model does not converge,
> which is far more useful than a score.

**It also retires a hypothesis the programme has been carrying all day.** The
E33 story was that five tasks truncated because 8,192 was too small. Two of
them (`parse_semver`, `word_break`) really were budget-limited and now pass.
`normalize_path` was not, and no budget we can afford will fix it.

**This makes the missing `medium` control decision-grade rather than tidy.**
`normalize_path` is a CORE-set task, and the E42 coding row that found `medium`
strictly better ran the EXPERT set - so **`normalize_path` has never been run
at `medium`**. Every observation of it is at `xhigh` or the template default
that resolves to `xhigh`. The competing hypothesis is now sharp:

- **If `medium` solves it quickly**, the entire E33 truncation story was an
  effort-level artifact misdiagnosed as a budget problem for a month, and the
  fix is a setting rather than a bigger machine.
- **If `medium` also fails to converge**, the task is genuinely beyond this
  model and the effort level is irrelevant.

Both readings are useful and they are cheaply separable, so the control is
**being queued now** (E47) rather than logged as a gap for a third time.

**Prediction 5 tracking:** registered "at least 3 of the 5 capped tasks return
`stop` instead of `length`". `parse_semver` yes, `normalize_path` yes
(`no_code` is a stop, not a cap). 2 of 2 so far - the prediction is about
escaping the cap, and both did, though only one produced an answer.

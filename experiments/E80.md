## E80 PRE-REGISTRATION - can a router aim the tool, and is the aiming cheaper than the harm? (2026-08-28)

**Registered before any scored arm runs.** A four-cell harness gate has run and
is declared below. **Four of twenty-four cells seen; no prediction is scored
against them.**

### Why this experiment exists

E79 measured both halves of the trade on the production model: offering the date
tool **gains** an item on 3 of 12 band-R items and **loses** one on 5 of 12
band-E items (6 counting one HTTP 500). Offered unconditionally it took the
workhorse from 13/24 to 11/24 and the registered tie-break said ship nothing.
E79's closing line was that H8/H19 routing is *"a precondition for the tools
branch, not an optimisation on top of it"*. This tests that.

| | |
|---|---|
| **which success question** | whether the tools branch is viable AT ALL on the resident production model, or whether E79 closed it |
| **uncertainty reduced** | whether a cheap classifier can aim the tool, given that a false positive costs about twice what a true positive buys |
| **decision that changes** | whether the routing guide gains a tool-routing rule, or whether counted-period work simply stays a model-swap |

### The ceiling, computed from banked E79 data and NOT a scored arm

Every L5 item is an independent single-turn request with the pack resent, so
arm A and arm B can be spliced per item: **take the tools-on result on band R
and the tools-off result on band E.** That is perfect routing, and it is free.

| | total | band R | band E |
|---|---|---|---|
| E79 arm A, tools off | 13/24 | 3/12 | 10/12 |
| E79 arm B, tools on | 11/24 | 6/12 | 5/12 |
| **ORACLE, perfectly routed** | **16/24** | 6/12 | 10/12 |

**Perfect routing buys +3 of 24.** For contrast, E78's tool-free Qwen3.8 on the
same bank is **23/24**. So this experiment cannot make the resident model
competitive with the model swap, and is not trying to: it decides whether the
tool is worth having on the model that is already loaded.

**The economics the router has to beat**, from the same arms:

| | rate |
|---|---|
| tool offered on a band-R item -> gains an item | 3/12 = **0.25** |
| tool offered on a band-E item -> loses an item | 5/12 = **0.42** capability, 6/12 = 0.50 including the HTTP 500 |

A router may therefore misfire on band E at no more than about **0.6x** its
band-R hit rate before the tool stops paying for itself. Precision matters more
than recall here, and `tools/tool_router.py` breaks ties toward NOT offering for
that reason.

### The arms

Answering model is Qwen3-30B-A3B throughout. The router sees the **question
only**, never the pack - a router that had to read the record to decide would
cost about what answering costs, which is what E75 found when disagreement
routing turned out not to be cheaper than the work it routed.

| arm | router |
|---|---|
| **R1** | `rule` - deterministic patterns, no inference, no latency |
| **R2** | `model` - the workhorse routes ITSELF, one YES/NO call per question, `router_thinking=off` |
| **R3** | `model` - **Qwen3-8B** routes, workhorse answers. The plan's H18 specialist-small-model claim |

### R1 IS FITTED AND ITS SCORE IS NOT EVIDENCE ABOUT ROUTING

`rule_router` was authored with this bank visible. Checked against the band
labels before registration it scores **12/12 band-R recall and 0/12 band-E false
positives** - it is the oracle by construction. **That number is declared here so
nobody reads it later as a result.**

R1 is still worth running, for one narrow reason: it proves the routed PIPELINE
reproduces the spliced oracle end to end. If R1 does not land on 16/24, the
splice above is wrong and every figure in this entry is suspect. It is a control,
not a finding, and the entry will report it as one.

**R2 and R3 are fitted to nothing** and they are the experiment.

### The harness gate, run before this registration

`tools/run_h6_date_arm.py` gained `--tools routed`, `--router`,
`--router-base-url` and `--router-thinking`; the per-item decision is recorded in
each result row. Four cells, rule router, declared and unscored:

| item | band | tool offered | outcome |
|---|---|---|---|
| `R03` | R | yes | `correct` - one `add_business_days` call |
| `R11` | R | yes | `off_by_calendar` - `date_diff` returned an exclusive 274, answered 274 |
| `E02` | E | **no** | **`correct`, 96,000** - the item arm B destroyed by spending six rounds on date arithmetic |
| `E09` | E | **no** | `correct` - the item arm B lost to an HTTP 500 |

### Predictions, each naming the FIELD it is scored against

| # | prediction | scored against |
|---|---|---|
| 1 | **control:** the routed pipeline reproduces the splice | R1 `total` = **16/24**, band R 6/12, band E 10/12 |
| 2 | **DISCRIMINATING: the model cannot tell a counting question from a lookup one.** E79 saw it call tools on 10 of 12 band-E items when merely offered | R2 band-E false positives **>= 4 of 12** |
| 3 | self-routing does not meaningfully beat not routing | R2 `total` **<= 14/24**, against arm A's 13 |
| 4 | the small specialist routes better than the answerer | R3 band-E false positives **<** R2 band-E false positives |
| 5 | no router beats perfect routing | every routed arm `total` **<= 16/24** |
| 6 | routing cannot manufacture a conversion the tool did not make | every routed arm band R `correct` **<= 6 of 12** |
| 7 | the YES/NO reply is parseable | `routing.parsed` false on **<= 1 of 24** in each of R2 and R3 |

**Prediction 2 is the one that decides the branch.** If the workhorse can route
itself, the tool becomes deployable on the resident model for the price of one
short call per question. If it cannot - and E79's behavioural evidence says it
may not - then aiming the tool needs a second model, at which point the honest
comparison is against simply using that second model to answer.

### Registered decision rule, tie-break included

| observed | action |
|---|---|
| R2 `total` >= 16/24 with band-E false positives <= 2 | **the tool is deployable on the resident model.** Recommend a tool-routing rule for the routing guide, with the per-question router call named as its cost |
| R2 `total` is 14-15 | **partial and honest:** report the gain and the router's error rates, and recommend nothing until a second bank confirms it. 24 items cannot support a serving change on a 1-2 item margin |
| R2 `total` <= 13 (arm A) | **self-routing fails.** The tools branch on this model needs a second model to aim it, and that comparison belongs against the model swap, not against arm A |
| R3 beats R2 by >= 3 with band-E FP <= 2 | the H18 specialist claim is supported HERE, and the next question is whether a 5 GiB router plus a 17 GiB answerer beats a 17 GiB answerer that is simply better - which is a memory-budget question, not a routing one |
| R1 != 16/24 | **stop.** The splice is invalid, the oracle figure is withdrawn, and nothing else in this entry may be quoted until the discrepancy is resolved |
| **tie-break:** R2 and R3 both land at 14-15 with band-E FP of exactly 3 | ambiguous. Do NOT recommend; report both error rates and note that the deciding measurement is a second bank, not a third router |

### Conditions, declared

- **Rule 9 breached and acknowledged; all wall times VOID.** The router's cost is
  therefore reported as **extra calls per question**, not as latency.
- `--router-thinking off` on both model routers. A router that reasons for forty
  seconds costs more than the answer it is aiming.
- R3 needs two servers resident: Qwen3-8B (~5 GiB) routing and the workhorse
  (~17 GiB) answering, plus the relay's 29.3 GiB - about **51 GiB**, clear of the
  60 GiB regime in `docs/memory-edge-deadlock.md`.
- An unparseable router reply is treated as NO and counted, never guessed.

**Evidence to be written:** `results/raw/e80-r{1,2,3}-l5.json`,
`results/raw/e80-scores.json`.


## E80 RESULT - the model CAN route itself, the small specialist cannot, and the margin is inside the harness's own noise. PREDICTIONS 2, 3 AND 4 FALSIFIED. (2026-08-28)

Three routed arms, 24 items, answering model Qwen3-30B-A3B throughout, tier
`l5`, `-c 16384`, `--jinja`, `-fa on`, `--max-rounds 6`, `router_thinking=off`,
kernel `7.0.0-29-generic`. **Rule 9 breached and acknowledged; all wall times
VOID.** Router cost is reported as extra calls, not latency.

| arm | router | total | band R | band E | band-R offered | **band-E false positives** | unparsed | vs tools-off |
|---|---|---|---|---|---|---|---|---|
| **R1** | rule (**fitted**) | **16/24** | 6/12 | 10/12 | 12/12 | **0/12** | 0 | **+3** |
| **R2** | the workhorse routes itself | **15/24** | 5/12 | 10/12 | 12/12 | **3/12** | 0 | **+2** |
| **R3** | Qwen3-8B routes | **12/24** | 6/12 | **6/12** | 12/12 | **6/12** | 0 | **-1** |

Reference points: E79 arm A tools-off **13/24**; the spliced oracle **16/24**;
E78's tool-free Qwen3.8 on the same bank **23/24**.

### THE ANSWER

> **The production model can route itself, and it was the small specialist that
> could not.** Asked one YES/NO question about the question, the workhorse
> misfired on 3 of 12 band-E items and lost nothing to them - its band E stayed
> at 10/12, identical to not routing at all. Qwen3-8B misfired on **6 of 12**
> and took the system to **12/24, worse than not routing.**

**Prediction 2 is the one I got wrong, and the reason is worth more than the
prediction.** I registered that the workhorse would misfire on at least 4 of 12,
on the strength of E79's behavioural evidence that it *called* the tool on 10 of
12 band-E items when the tool was merely offered. It misfired on 3.

> **Deciding implicitly whether to use a tool, and answering explicitly whether a
> question needs one, are different capabilities in the same model.** E79's
> behaviour did not predict E80's classification. A model that reaches for a date
> tool on a liability-cap question will, if asked first, correctly say that
> question does not need counting.

### The H18 specialist claim is falsified in the damaging direction

Prediction 4 registered that the small model would route BETTER. It routed twice
as badly - 6 false positives against 3 - and four of the six destroyed their
item (`E02`, `E03`, `E05`, `E08` to `format_error`). The plan's H18 proposes
small specialists for exactly this role. **On this task the 5 GiB specialist was
worse than the 17 GiB generalist doing the job itself, and worse than doing
nothing.**

### R1 was the registered stop-condition and it passed

R1 landed on **16/24, band R 6/12, band E 10/12** - the spliced oracle exactly.
The registered rule was that any other figure invalidates the splice and
withdraws the 16/24 ceiling from the record. It held, so the ceiling stands and
R2 and R3 are measurable against it.

**R1 remains fitted and is not evidence about routing.** Its 12/12 recall and
0/12 false positives were authored with the bank visible and were declared
before the run.

### R2's three misfires are two defensible readings and one real error

| item | router said | is it wrong? |
|---|---|---|
| `E05` | YES | *"HOW MANY state a Notice Period of their own, and which ones?"* - the answer contains a count. A router answering YES is defensible |
| `E08` | YES | *"...what Acceptance Window does that Call-Off Order state? Give the document ID and the number of Business Days."* - also asks for a number |
| `E12` | YES | *"How many employees does Northgate Systems have?"* - counting LANGUAGE over an absent fact. The only clear misroute |

The band label marks what makes an item **hard**, not whether a number appears in
the answer, so the raw false-positive metric is harsher on this router than the
questions warrant. **None of the three cost an item.**

### THE CAVEAT THAT BOUNDS THE HEADLINE, and it is a real one

Outcomes under tool offering are **not fully reproducible across arms in this
harness.** Of the items offered the tool in more than one arm:

| item | E79-B | E80-R2 | E80-R3 |
|---|---|---|---|
| `E02`, `E03` | format_error | (not offered) | format_error |
| `E12` | correct | correct | correct |
| `E05` | correct | correct | **format_error** |
| `E08` | **format_error** | **correct** | format_error |
| `R09` | correct | **off_by_calendar** | correct |

**Three cells diverge, and two of them are in R2** - the only arm that shares one
server between routing and answering, so its answering requests follow router
traffic through the same slot and prompt cache. That is a **candidate mechanism,
named and NOT established**: the multi-round tool loop injects tool results into
the context, so cache state differs from a cold slot in a way single-turn work
does not, and E77's measured zero noise floor was for single-turn answers.

**What it costs the headline, stated rather than buried:** had `E08` died as it
did in the other two arms and `R09` lived as it did in the other two, R2 would
read anywhere from **14/24 to 16/24**. So **R2's +2 carries a +/-1 to 2 item
instability that this experiment measured and did not control.** No conclusion
below leans on the exact figure.

### Scoring

| # | prediction | outcome |
|---|---|---|
| 1 | R1 = 16/24, band R 6/12, band E 10/12 | **HELD exactly** - the splice is valid and the ceiling stands |
| 2 | R2 band-E false positives >= 4 of 12 | **FALSIFIED** - 3, and none cost an item |
| 3 | R2 `total` <= 14/24 | **FALSIFIED** - 15 |
| 4 | R3 band-E false positives < R2's | **FALSIFIED in the opposite direction** - 6 against 3 |
| 5 | every routed arm `total` <= 16/24 | **HELD** - 16, 15, 12 |
| 6 | every routed arm band R `correct` <= 6/12 | **HELD** - 6, 5, 6 |
| 7 | `routing.parsed` false on <= 1 of 24 in R2 and R3 | **HELD** - zero in both |

### The registered decision rule fires on its middle branch

> *"R2 `total` is 14-15 -> partial and honest: report the gain and the router's
> error rates, and recommend nothing until a second bank confirms it. 24 items
> cannot support a serving change on a 1-2 item margin."*

**R2 is 15/24. Nothing is recommended and the routing guide does not change.**
The instability documented above makes that branch more right than it was when
it was written: a +2 margin with a +/-2 wobble is not a serving decision.

The R3 branch - *"R3 beats R2 by >= 3 ... the H18 specialist claim is supported
HERE"* - does not fire, and its inverse is the finding.

### What survives, and what it means for the programme

- **Routing works in principle and the ceiling is small.** Perfect routing is
  +3 of 24; the best real router got +2, inside its own noise. The tools branch
  is not dead, and it is not worth a serving change on this evidence.
- **The router does not have to be a second model.** That was the assumption
  behind sending this question to H18, and it was wrong here.
- **Even perfectly aimed, the tool leaves a lot on the table.** R1 offered the
  tool on exactly the right twelve items and still logged `result_ignored` four
  times and `wrong_args` twice - band R 6/12 against Qwen3.8's tool-free 11/12.
  **Perfect aiming does not produce perfect use**, and the gap between the two is
  the same reasoning capability the tool was brought in to substitute for.

### What this does NOT establish

- **One bank, 24 items, 12 per band.** Every figure carries an interval wider
  than the +2 it reports.
- **One question form for the router.** A different prompt might route better or
  worse; only `ROUTER_PROMPT` at `tool-router-v1-2026-08-28` was measured.
- **The divergence mechanism is unresolved.** The shared-server hypothesis is a
  candidate. **Reopen condition:** re-run R2 with `--router-base-url` pointing at
  a second copy of the workhorse, so routing and answering never share a slot. If
  the three divergent cells stop diverging, the mechanism is the cache and every
  multi-round tool figure in E79 and E80 needs that control.
- **Nothing about latency.** Rule 9 breached; the router's cost is one extra
  short call per question and is reported as such.

## E80 ADDENDUM - PRE-REGISTRATION: is the divergence router traffic on the answering slot? (2026-08-28)

**Registered before the control runs.** E80's entry named a reopen condition and
this executes it, with one substitution declared up front.

### The literal control is REFUSED on memory grounds

The reopen condition as written was *"re-run R2 with `--router-base-url` pointing
at a second copy of the workhorse"*. Priced before being attempted:

| | |
|---|---|
| answering workhorse, `-c 16384` | ~18.8 GiB |
| second workhorse as router, `-c 2048` | ~17.5 GiB |
| sparkrouter relay, resident and measured | **29.307 GiB** |
| **total** | **~65.5 GiB** |

That is over the ~60 GiB regime in `docs/memory-edge-deadlock.md`, unattended,
on an account that cannot power-cycle the box. **It is not run.** The condition
was written without pricing it, which is the error being corrected here.

### The substitute isolates the same variable more tightly

`--router fixed --router-decisions` replays R2's recorded per-item decisions and
makes **no router call at all**. Against R2 that changes exactly one thing:
whether router traffic passed through the answering slot before the answer.
Same model, same 15-of-24 decisions, same prompts, one server, ~18.8 GiB.

It is a better control than the two-server version, which would have varied
slot-sharing AND introduced a second resident process competing for bandwidth.

### Predictions, each naming the FIELD it is scored against

R2 diverged from every no-router-traffic arm on exactly two cells. The control
says which side they land on.

| # | prediction | scored against |
|---|---|---|
| 1 | `R09` returns to the value every other arm gave | `R09` outcome = **`correct`** (R1, R3 and E79-B all `correct`; R2 alone `off_by_calendar`) |
| 2 | `E08` returns to the value the other tool-offered arms gave | `E08` outcome = **`format_error`** (E79-B and R3 both `format_error`; R2 alone `correct`) |
| 3 | validity check, not a finding | the replay arm offers the tool on exactly **15 of 24** items, matching R2 by construction |

### Registered decision rule

| observed | action |
|---|---|
| predictions 1 and 2 both hold | **the mechanism is router traffic on the answering slot.** Record it as a harness property, and note that every multi-round tool figure in E79 and E80 carries a per-item instability of this size |
| neither holds - the replay reproduces R2 | **the shared-slot hypothesis is REFUTED.** The divergence is something else and stays unresolved; do not offer a mechanism |
| exactly one holds | **unresolved, and say so.** One cell either way is not a mechanism, and a 1-of-2 result must not be reported as partial support |
| the replay arm's decisions are not 15 of 24 | the replay is broken. Stop and fix before reading anything else |

**No headline moves whichever way this lands.** E80 already recommends nothing,
and this decides whether the instability gets a named cause or stays an
unexplained wobble.

**Evidence to be written:** `results/raw/e80-r2ctl-l5.json`.

## E80 ADDENDUM RESULT - it IS router traffic on the answering slot. Both predictions held, and a replicate closed the alternative. (2026-08-28)

| | `R09` | `E08` | total | band R | band E | tool offered |
|---|---|---|---|---|---|---|
| E79-B (no router traffic) | correct | format_error | - | - | - | on |
| E80-R3 (router on a SEPARATE server) | correct | format_error | 12/24 | 6/12 | 6/12 | routed |
| **E80-R2 (router SHARES the answering server)** | **off_by_calendar** | **correct** | 15/24 | 5/12 | 10/12 | routed |
| **CONTROL - R2's decisions replayed, no router call** | **correct** | **format_error** | 15/24 | 6/12 | 9/12 | routed |

### Scoring

| # | prediction | outcome |
|---|---|---|
| 1 | `R09` = `correct` in the control | **HELD** |
| 2 | `E08` = `format_error` in the control | **HELD** |
| 3 | the control offers the tool on 15 of 24 | **HELD** - identical to R2 by construction |

**The control differs from R2 on exactly the two predicted cells and no others.**
Twenty-two of twenty-four reproduce R2 precisely.

### The replicate closes the alternative explanation

Two predicted cells could equally have been a near-boundary wobble that flips on
any re-run, which would make the control a coincidence rather than a mechanism.
So the control was run a second time, same configuration:

> **24 of 24 answers byte-identical. 24 of 24 call counts identical. Zero
> differing outcomes.**

**The multi-round tool loop is fully deterministic when the answering slot sees
no router traffic.** So the difference from R2 is attributable to the one
variable the control changed.

### The registered rule fires

> *"Predictions 1 and 2 both hold -> the mechanism is router traffic on the
> answering slot."*

**Recorded as a harness property, and it is narrow:** with `-np 1`, a router
request served by the SAME `llama-server` process passes through the same slot
and prompt cache before the answer, and in a multi-round tool loop that is enough
to change an outcome. E77 measured a zero noise floor for single-turn answers on
this model; that result does not extend to this loop, and now the boundary
between the two is measured rather than assumed.

**Which figures this touches, stated exactly so nobody over-corrects:** only
**E80's R2**. E79's arms make no router calls, E80's R1 makes none, and E80's R3
routes on a separate server. **No headline moves** - R2 is 15/24 either way, the
decision rule's middle branch fires either way, and E80 recommends nothing either
way. What changes is the composition: the control's band R 6/12 and band E 9/12
is the cleaner measurement of routing with R2's decisions.

### One divergence is NOT explained, and it is the more interesting one

E80 recorded three divergent cells. This control explains two. **`E05` is not one
of them**: it diverged in R3, whose answering server never saw a router call
(the 8B routed on a separate port). So router traffic cannot be its cause.

What R3 did have was a different **history through the answering slot** - it
offered the tool on 6 band-E items against R2's 3, so more tool loops ran before
`E05` arrived. That suggests the general form: **the answering slot's history
affects outcomes in a multi-round loop, whether that history is router calls or
earlier tool loops.** The control establishes the first. **The second is a
hypothesis and is not established here**, and the cheap test is a fixed-decision
arm run in two different item orders.

### The reusable rule this earns

> **Do not share one `llama-server` between a router and the answerer it routes
> for.** It costs a second process, and the alternative is a per-item
> instability that looks exactly like a capability difference.

The corrected reopen condition for anyone repeating this: the literal two-model
control is ~65.5 GiB alongside the resident relay and must not be run
unattended. Replaying recorded decisions isolates the same variable at ~18.8 GiB.

**Evidence:** `results/raw/e80-r2ctl-l5.json`,
`results/raw/e80-r2ctl-rep-l5.json` (the replicate).

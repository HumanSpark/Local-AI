## E39: the EXPERT coding tier - does anything here separate a generalist from a coder model? (2026-08-15, pre-registered before any run)

**Why this exists.** E33's core tier does not locate a frontier: a cheap
cloud model scored 14/15 on it. The owner's instruction was explicit - build
the expert tier BEFORE quoting any cloud coding verdict. E33's registration
covers the 15 core tasks only, so the expert set needs its own predictions
and this is them.

**What makes these tasks hard, and what deliberately does NOT.** Difficulty
comes from EXACTNESS, not obscurity: stated contracts (laziness,
non-mutation, atomicity), complexity gates enforced by measurement, specified
tie-breaks, and edge-case grammar. Nothing here requires an unusual algorithm
or a library trick. A competent engineer reading the spec carefully can pass
every one; a model that pattern-matches to the nearest familiar problem
cannot.

**Eight tasks** (`spikes/coding-eval/expert_tasks.py`): `glob_match`,
`round_decimal`, `kmerge`, `wrap`, `sliding_median`, `apply_patch`,
`interval_map`, `parse_csv`.

**Every task is validated against BOTH a reference that must pass and one or
more naive solutions that must fail** (`tools/validate_expert_tasks.py`). A
task that everything passes is a broken task, and three were caught and
rewritten that way before any model saw them: `sliding_median` assumed a
complexity gap without measuring it, `interval_map` squeaked under the
timeout, and `wrap`'s naive accidentally implemented the required tie-break
by scanning in the other direction.

**The complexity gates are enforced by MEMORY as much as by time, and this
was measured through the runner's own `run_candidate` rather than assumed:**

| task | reference | naive |
|---|---|---|
| `interval_map` | pass, 0.54s | error, 9.18s (4 GB exhausted) |
| `sliding_median` | pass, 0.55s | timeout, 15.02s |

Without the 4 GB `RLIMIT_AS` the `interval_map` naive does not fail - it
consumes a 128 GB box, which is the 03:12 OOM of this same night. An
unbounded runner would have scored that naive solution as a PASS.

**Config.** `tools/run_coding_eval.py --task-set expert`, llama-server
b10435, `-c 32768`, `-np 1`, temperature 0, `max_tokens 24576` (matching E33
Amendment 2, so truncation is not re-learned as a finding), candidate
execution bounded at 15s wall and 4 GB.

**Arms.** Qwen3.8-27B-Q4_K_M (subject); Qwen3-Coder-30B-A3B (the incumbent
coding pick); Qwen3-30B-A3B-Instruct-2507 (the workhorse).

**Predictions (registered before any arm runs). The FIELD is named in each.
Bands are set deliberately WIDE and somewhat high, because E37 falsified four
of five predictions by under-estimating this model and the correction must
apply here too, not just in hindsight.**

1. **`pass` count out of 8.** Qwen3.8 **2-5**; Qwen3-Coder-30B **2-5**;
   workhorse **0-3**.
2. **`truncated` count at 24576 is 0-2 for Qwen3.8.** E33 at 8192 produced 5
   truncations in 6 failures. If the expert tier - harder problems, more to
   reason about - still truncates 3 or more at three times the budget, the
   non-termination reading in E33 Amendment 2 is confirmed on a second task
   set, which is a stronger result than either run alone.
3. **The two complexity-gated tasks are the least passed.** `sliding_median`
   and `interval_map` together yield **0-1 of 2** for every local arm.
   Recorded field: `outcome` for those two ids, per arm.
4. **At least one arm fails `apply_patch` on the CONTRACT rather than the
   logic** - producing code that computes the right patch but mutates the
   input document, or leaves earlier operations applied after a later one
   fails. Recorded field: `outcome == "wrong_answer"` on `apply_patch` with
   the reference logic otherwise correct.
5. **The discriminating claim: Qwen3.8 >= Qwen3-Coder-30B on `pass` count.**
   This is the coding half of the routing question. E33's core-tier answer is
   not quotable (5 of 6 failures were truncations), so this tier carries it.

**Not predicted:** which individual tasks fail, beyond the two named in (3).

**Two falsifiers, and they point in opposite directions.**

- **If any arm scores 8/8, the expert tier is saturated too** and the coding
  ceiling is still unmeasured - the same outcome E38 guards against on the
  knowledge-work side.
- **If EVERY arm scores 0 or 1 of 8, the tier is too hard to discriminate.**
  A set nothing passes ranks nothing, and an intermediate level would be
  needed before any verdict rests on it. This is the likelier failure given
  the tasks were tuned against naive solutions rather than against real model
  output.

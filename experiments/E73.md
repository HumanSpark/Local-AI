## E73 PRE-REGISTRATION - C-H1 pilot: does the real-commit coding instrument DISCRIMINATE? (2026-08-19)

**Registered BEFORE any run.** This is a discrimination gate, not a rate
measurement, and saying so before the run is the point. Five usable tasks
against four arms is 20 cells - enough to learn whether the instrument separates
the arms, nowhere near enough to state "x% of coding work can be handed over".

### Why this experiment exists

| | |
|---|---|
| **which success question** | *What percentage of my Claude Sonnet coding workload can I hand to the local machine without supervising it?* |
| **uncertainty reduced** | there is currently NO measurement of these four arms on real-repository tasks with held-out ground truth. F33 is one model pair on two tasks; F36 is three arms on synthetic fixtures a frontier model clears in under 50s |
| **decision that changes** | whether to author the remaining 10-15 tasks at all, and which arm is the C-H1/C-H2 candidate. If the instrument does not separate four very different arms, authoring more of the same tasks is wasted work |

### The arms - four, not three

Per AMENDMENT 3 correction 4. The owner's workplan listed workhorse,
Qwen3.8-27B and gpt-oss-120b, all three of which were selected by document and
knowledge benchmarks - the exact method F33 records as **non-predictive of
coding competence**. **Qwen3-Coder-30B-A3B is included as the reigning route**,
and excluding the incumbent from its own bake-off would have been the error.

| arm | model | why it is here |
|---|---|---|
| `workhorse` | Qwen3-30B-A3B-Instruct-2507 | serves 91.3% of real traffic; F33 scored it 0 on real repos |
| `coder` | Qwen3-Coder-30B-A3B | the current local coding route (F33) |
| `qwen38` | Qwen3.8-27B | dense reliability reference; best local AABR arm (E69) |
| `gptoss` | gpt-oss-120b | strongest difficult-tier arm; supervised-only per E71 |

### The tasks, and what makes them ground truth

Five of six passed the gate in `tools/ch1_tasks.py`: **C01, C03 (interactive,
30s budget), C04, C05, C06 (substantial, 300s budget)**. Each reverts one source
file to its state before a real commit in this repository; the commit's own test
file is removed from the sandbox and injected only at grading.

**C02 was REFUSED** because its held-out test still passes after the revert, so
every arm would score correct on it. That is the gate doing its job, and the
refusal is recorded rather than the task quietly dropped.

**Restore-then-inject, in that order.** Every `tests/` file is returned to its
pre-run state before the held-out tests arrive, so F36's failure - deleting a
test that cannot be satisfied and declaring success - cannot produce a pass. The
attempt is still counted: `guard.attempted_test_destruction` fires on the
filesystem evidence whether or not the command screen caught it.

### Serving config, declared (Rule 8 / F39)

`llama.cpp/wt/b10435`, `-c 32768 -np 1`, one arm resident at a time (Rule 9),
max 60 agent turns, 900s hard ceiling per task, tools: `read_file`, `edit_file`,
`bash`, `search`. Kernel 7.0.0-28, Vulkan/RADV gfx1151.

**The 900s hard ceiling exceeds the 300s substantial budget deliberately.** A
task that finishes correctly at 400s has failed `success_at_deadline` and
succeeded at `completed_correct`, and those must be separable. Cutting the run
at the budget would destroy the distinction and record a capability failure that
was a latency failure.

### Metrics recorded per cell, kept apart

`completed_correct` (held-out tests pass), `success_at_deadline` (correct AND
within the tier budget), `wall_s`, `turns`, `tool_calls`, `malformed_calls`,
`prompt_tokens`, `generated_tokens`, `non_termination`, `infrastructure_failure`,
`critical_error`, `regression_suite` (the rest of the suite, run separately),
and the full guard report.

**Four failure classes stay separate** (F87): wrong answer, non-termination,
infrastructure failure, and critical error. A cell that fails because the server
died is not evidence about the model.

result worth having early.

## CLOSE-OUT CORRECTION - two estimators were used for one quantity, and one bound was attached to the wrong n (2026-08-20)

**Trigger:** re-deriving the headline intervals for the final report. Three
published bounds on zero-event rates did not come from the same estimator, and
the tool that produced them said they did.

### The defect in the instrument

`tools/wilson_ci.py` v1 special-cased `k == 0` and `k == n`, returning the
**exact one-sided bound** `1 - alpha**(1/n)` (Clopper-Pearson) from a function
named `wilson_ci_95` and documented "95%, two-tailed". Every interior
proportion got a real Wilson interval. So the programme published zero-event
bounds from one estimator and everything else from another, under one name.

**No figure was arithmetically wrong.** Every one is a correct 95% bound of its
own kind. They are not comparable with each other, which is the like-for-like
failure - the same shape as E32's prediction 1, found in the same week.

### The three published figures, traced exactly

| published | where | what it actually is | correct for that n? |
|---|---|---|---|
| **0/20 -> 0.0-16.1%** (coding) | interim report, E73 | two-sided Wilson, n=20 | **yes** |
| **0/25 -> 11.29%** (E71 soak) | E71 entry | exact one-sided, n=25 | **yes** |
| **0/125 -> 2.95%** (E72 soak) | E72 entry, interim report, F57 addendum | exact one-sided, **n=100** | **NO - wrong n** |

**2.95% is the bound for E72's 100 cold loads alone.** It is quoted throughout
as the bound from the combined **125** cycles (E71's 25 plus E72's 100). For
n=125 the same estimator gives **2.37%**, and two-sided Wilson gives **2.98%**.

### What the numbers are, stated to the unit

| n | events | exact one-sided 95% upper | two-sided Wilson 95% upper |
|---|---|---|---|
| 20 | 0 | 13.91% | **16.11%** |
| 25 | 0 | **11.29%** | 13.32% |
| 100 | 0 | **2.95%** | 3.70% |
| 125 | 0 | **2.37%** | 2.98% |

**The canonical estimator from close-out is two-sided Wilson 95%**, because it
is what every non-zero rate in this programme already uses and mixing is the
defect. On that estimator the S-H2 bound over 125 cycles is **2.98%**, not
2.95%.

### No decision moves, and that is stated rather than assumed

- **S-H2 / unattended use.** 2.37%, 2.95% and 2.98% sit on the same side of
  every threshold this programme registered. The conclusion - gpt-oss-120b is
  cleared for supervised batch use and not for unattended use without a
  watchdog - is unchanged.
- **E71's 11.29%.** Its registered rule needed a bound far below this to clear
  unattended use. At 13.32% it still does not clear it. Unchanged.
- **E73's 16.1%.** Already Wilson. Unchanged.

### What changed in the instrument

`tools/wilson_ci.py` is now **`wilson-v2-2026-08-20`**: Wilson everywhere,
including both extremes, so the function's name describes its value. The exact
one-sided bound stays available as `exact_upper_bound_one_sided()` - it is the
right tool for "we saw no failures in n trials, how bad could the rate be?" and
is simply not interchangeable with a two-sided interval. `tests/test_wilson_ci.py`
pins the zero-count case to the closed form `z^2 / (n + z^2)`, pins the published
16.1%, and asserts that the two estimators **genuinely disagree** - so a future
change that quietly makes them coincide fails a test instead of passing silently.

**Historical entries are NOT rewritten.** E71 and E72 keep the figures they were
scored against, and this entry is the correction of record. Documents written at
close-out use the Wilson figure and say which estimator they used.

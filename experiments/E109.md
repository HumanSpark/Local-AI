## E109 PRE-REGISTRATION - is the HARNESS a lever on OUTCOMES, on coding and on knowledge work? (2026-09-05)

**Registered before either arm runs.** `results/raw/e109` does not exist.

### Why this experiment exists

E108 stage 1 answered ADMISSIBILITY: Aider and Hermes fit on this box, Claude
Code does not. **It says nothing about whether swapping an admissible harness
changes what you get**, which is the question that decides whether this area is
worth further investment.

| | |
|---|---|
| **which success question** | local agentic work - and whether harness choice is a lever at all |
| **uncertainty reduced** | whether two harnesses driving IDENTICAL WEIGHTS produce different outcomes, on coding AND on knowledge work |
| **decision that changes** | what `tools/local-code` wraps, and whether harness research continues or closes |

**The knowledge-work half has never been asked here.** Every L1-L5 figure in
this repo is a bare API call: one request, full documents in context, no tools,
no iteration. A harness is a different thing entirely - instructions, tool
access, the option to re-read. Whether that scaffolding HELPS or HURTS document
work is unmeasured, and it is the shape a real RAG deployment takes.

### The model is held constant. That is the whole design.

Both arms serve `Qwen3.8-27B-Q4_K_M` from the same build at the same settings.
**Any difference is the harness**, because nothing else moves. This is the
inverse of every other experiment in this register, which held the harness fixed
and varied the model.

### Arm A - CODING

| | |
|---|---|
| instrument | `tools/aider-tasks.json`, the 3 real-commit tasks, executed and verified |
| arms | **Aider** (incumbent) vs **Hermes**, same model, same tasks, same repo state |
| primary | tasks passing their independent `verify` command |
| secondary | wall time, total tokens, and whether the harness's own exit code agrees with the verdict |

F113 measured Aider exiting 0 on nine runs, four of which were no-ops. **The
exit-code question is asked of Hermes too**, because a harness that cannot
report its own failure is a poor system component regardless of capability.

### Arm B - KNOWLEDGE WORK, and why it is not defeated by saturation

L5 gives a bare API call 23/24 (F142: saturated for MODEL comparison). **It is
not saturated for this question, because the harness arm can lose.** There are
23 points of room below, and the interesting outcome is whether scaffolding
costs accuracy.

| | |
|---|---|
| instrument | the L5 24-item bank, same grader |
| **control** | the banked bare-API arm at `temperature 0`: **23/24, band R 11/12, band E 12/12** (E102/E107, reproduced three times) |
| **harness arm** | the same 24 questions asked through Hermes, with the ten documents **on disk as files** rather than pasted into context |
| primary | `correct` of 24, and `over_claim` of the 4 underspecified items |

**The document-delivery difference is deliberate and is the point.** Pasting the
pack into one request is what we measure today; putting it on disk and letting
the harness read it is what a deployed system does. If the harness arm loses
items it is retrieval failure, and that is a finding a client needs.

### Predictions, each naming the FIELD it is scored against

| # | prediction | scored against |
|---|---|---|
| 1 | **CODING: the harness changes the outcome** | Aider `passed` minus Hermes `passed` on the 3 tasks, **absolute difference >= 1** |
| 2 | **KNOWLEDGE: scaffolding COSTS accuracy** | Hermes `correct` **<= 21** of 24, against the bare-API control's 23 |
| 3 | **DISCRIMINATING: the loss is retrieval, not reasoning** | of Hermes' misses, **more than half** are items whose governing document it never read (checked from its tool-call log) |
| 4 | the harness does not increase fabrication | Hermes `over_claim` **<= 1** of 4, against the control's 0 |
| 5 | exit codes remain unreliable | at least one arm exits 0 on a task its `verify` command fails |
| 6 | both arms complete | `transport_failed` = 0; each arm produces a scored result for every item |

**P2 is registered in the direction that costs us nothing to be wrong about.** If
scaffolding turns out to HELP a saturated bank, that is a better result than the
prediction and a strong reason to keep investigating.

### Registered decision rule - and it decides the PROGRAMME, not just the arms

| observed | action |
|---|---|
| P1 holds and P2 holds | **the harness is a real lever in both directions.** Continue investigating; install and measure Goose and OpenCode as E108 stage 2 |
| P1 holds, P2 fails (knowledge unaffected) | the harness is a CODING lever only. Keep Aider/Hermes work, and **close the knowledge-work harness branch** |
| **P1 fails and P2 fails** | **two admissible harnesses produce the same outcomes on the same weights. The harness is an ADMISSIBILITY gate, not a quality lever - and this area CLOSES** beyond keeping a fitting client |
| P2 holds and P3 fails | scaffolding costs accuracy for a reason other than retrieval. That is more interesting than the headline and earns a follow-up |
| any arm cannot be driven headlessly | report the operational blocker; do not substitute a different task to rescue the arm |

### What this cannot establish

- **Two harnesses, three coding tasks, 24 knowledge items.** Small. P1's
  threshold of 1 task in 3 is coarse and is stated as such.
- **One model, one quant.** Nothing about whether the harness ordering is the
  same on a different model - which is precisely the transfer F85 warned about.
- **Nothing about the harnesses' own quality of life** - config, resumability,
  editor integration - which the owner may weigh independently.
- **Hermes' default toolset**, not a tuned one. E108 stage 1b tests whether
  disabling toolsets moves the schema; a tuned Hermes is a different arm.


### ⚠️ E109 AMENDMENT 1, declared 2026-09-05 17:35, AFTER arm B and BEFORE arm A is scored

Three registration defects, declared before any E109 score is written.

**1. P2 will hold on the letter and is FALSIFIED on the mechanism.** It reads
"scaffolding COSTS accuracy - Hermes `correct` <= 21 of 24". Arm B returned 19,
so the threshold is met. **But the loss is not accuracy.** Of the 5 items short
of the control's 23: **3 are `transport_failed`** (no response inside 600 s),
**1 is `format_error`** (my `ANSWER:` extractor could not parse a free-form
agent reply), and **1 is a wrong answer**. Accuracy among items that RETURNED is
**19/20**, against the control's 23/24 - the same rate.

Scoring this as "scaffolding costs accuracy" would be E64's failure exactly: a
prediction matching a field it was not about. **E109 therefore reports two
numbers wherever arm B is quoted - accuracy among returned items, and completion
rate - and never a single fraction.** Rules 13 and 14 already say why: an item
that was never answered was never answered, and scoring it as a miss reports the
transport as capability.

**2. P3 is UNSCORABLE and is withdrawn, not scored.** It reads "the loss is
retrieval, not reasoning", scored from `docs_mentioned`. Two independent reasons
it cannot be answered: **band E came back 12/12**, so there is no retrieval loss
to attribute; and the detector is unreliable, having fired on only 3 of 24 items
whose answers were plainly document-grounded. It asks about a failure that did
not occur, using an instrument that does not work. **Withdrawn as a registration
defect. It is not evidence of anything, in either direction.**

**3. The knowledge-work axis has ONE arm, so it ranks nothing.** Only Hermes was
run on L5; Aider is a code editor and cannot be an arm there. What arm B
measures is **scaffolding versus no scaffolding**, not harness A versus harness
B. Any "top harness" conclusion for knowledge work is therefore unavailable from
this experiment, and the decision rule's branches must be read as being about
*whether scaffolding is a lever*, not *which harness wins*.

**Arm A's configuration is also restated here.** Two earlier configurations are
DISCARDED and reported nowhere as results: `--edit-format diff` on what is file
creation (both tasks ran out an 1800 s clock), and `whole` with git, streaming
and no declared context (`glob_match` ran out 900 s). Neither measured Aider.
The scored arm mirrors Aider's own `benchmark.py`: `--no-git --no-stream
--cache-prompts --no-suggest-shell-commands --edit-format whole` plus a
`--model-settings-file` declaring the real 32,768 context, every flag verified
present in `aider 0.86.2` via `--help`.


## E109 RESULT - the harness is affordable on knowledge work and unaffordable on hard coding, and the reason is the MODEL it wraps (2026-09-05)

Model held constant throughout: `Qwen3.8-27B-Q4_K_M`, build `b10435`, kernel
`7.0.0-29`. Read with **AMENDMENT 1**, declared before any of this was scored.

### Arm B - knowledge work, Hermes with the ten documents ON DISK

| | bare API (control, reproduced 3x) | Hermes, docs on disk |
|---|---|---|
| **band E (evidence)** | **12/12** | **12/12** |
| band R (reasoning) | 11/12 | 7/12 |
| **over_claim** | **0** of 4 | **0** of 4 |
| total | 23/24 | 19/24 |

**Reported as two numbers, per Amendment 1:**

- **accuracy among items that returned: 19 of 20** (control: 23 of 24 - the same rate)
- **completion rate: 20 of 24** - 3 `transport_failed` at the 600 s cap, 1 `format_error`

> **Scaffolding does not degrade evidence work.** Hermes went and read the
> documents off disk and matched the bare API **exactly** on the band most
> exposed to retrieval failure - 12/12, the item type that turns on which of
> four parallel instruments governs. It fabricated nothing, on the four items
> built to tempt it. **What it costs is completions, not correctness.**

Of the five items short of the control, **one is a wrong answer**. The rest are
transport and my own output parser.

### Arm A - hard coding, Aider configured as its own maintainers benchmark it

| task | bare API (E104) | via Aider, benchmark config |
|---|---|---|
| `glob_match` | **pass**, 13,836 tokens | **harness_timeout** at 3,600 s |
| `kmerge` | **pass**, 4,692 tokens | **harness_timeout** at 3,600 s |
| `parse_csv` | pass, 6,848 tokens | **harness_timeout** at 3,600 s |

**FINAL: 0 of 3.** All three tasks ran the full hour without completing, on an
idle GPU, in the maintainers' own benchmark configuration. `exit_code_disagreements`
is 0 - but only because a timeout kills the process before it can exit 0 falsely,
so F113's exit-code defect is masked here rather than absent.

`--no-git --no-stream --cache-prompts --no-suggest-shell-commands --edit-format
whole` plus a settings file declaring the real 32,768 context; every flag
verified present in `aider 0.86.2`. Quiet GPU.

**`kmerge` is the decisive one.** It cost **4,692 tokens** as a single call - one
of the cheapest tasks in the tier - and did not finish in an hour through a
harness. Aider is bounded at `max_reflections = 3` (verified at line 101 of the
installed `base_coder.py`), so this is not an unbounded loop. In `whole` format
each reflection re-sends the system prompt, the full spec and the entire file,
so the harness pays prefill AND generation repeatedly. **At ~12 tok/s decode on
a 27B dense model, that compounds past an hour on a task worth five thousand
tokens.**

### THE ANSWER, and it is about the interaction rather than the harness

> **The harness is not independently good or bad. Its affordability is set by
> the model it wraps.**
>
> F112 measured Aider's first turn at **3.9 s median** on the workhorse
> (`Qwen3-30B-A3B`, a 3B-active MoE). The same harness on a 27B DENSE model
> cannot finish a 4,692-token task in an hour. Same client, same box, same day's
> code - a difference of three orders of magnitude, produced entirely by which
> model sits behind it.
>
> **An iterative harness multiplies the model's per-token cost by its turn
> count.** That is affordable at 3B active and unaffordable at 27B dense. The
> lever is not "which harness" - it is "does this model's speed support an
> iterative harness at all".

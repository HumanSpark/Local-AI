## E79 PRE-REGISTRATION - can a deterministic tool close the band-R gap between the FAST model and the ACCURATE one? (2026-08-28)

**Registered before any arm runs.** A two-item harness gate has run - `R03` and
`R11` on the production model with tools on - and its outcome is declared below
rather than hidden. **Two of twenty-four cells have been seen and no prediction
below is scored against them.**

### Why this experiment exists

E78 measured the production model at **3/12** on band R and Qwen3.8-27B at
**11/12**, an eight-point gap. It also measured the price of that gap: the
workhorse answers band-R items in under a second and Qwen3.8 takes 45-60
seconds each. E78's recommendation was to move the programme onto tools, and
this is that move.

| | |
|---|---|
| **which success question** | the routing decision. `reports/2026-07-16-local-model-routing-guide.md` currently sends counted-period work to the slow model |
| **uncertainty reduced** | whether a deterministic tool lets the FAST model do work it currently cannot, rather than only making a weak model less weak |
| **decision that changes** | if the gap closes, the routing guide keeps the workhorse resident and hands it a tool instead of swapping models for a class of task |

### What is already known, and why this is not E67 again

**E67 ran the date tool on L4's six date questions** and found it *"rescues the
weak model and damages the strong one"*: the workhorse went **0/6 -> 4/6** with
four conversions and zero regressions, while gpt-oss-120b went **5/6 -> 4/6**.

Three things make this a different question:

1. **E67's control was at the floor.** 0/6 means its registered
   regression-prediction was untestable - nothing could regress from zero. Band
   R's control is 3/12, so regressions are measurable.
2. **Band R is a wider mechanism mix than six date questions**: business-day
   walks against a holiday list, month-end clamping, parallel periods, interest
   arithmetic and a composition item. The tool addresses some of those and
   provably cannot address others.
3. **E67 used `TOOL_SCHEMA_V1`**, three date primitives, which cannot count
   Business Days at all. This runs **V2**, which adds `add_business_days`,
   `roll_to_business_day` and `weekday`. V1 stays frozen and the default, so
   E67 and E68 keep the configuration their results are attributed to.

### The harness gate, run 2026-08-28 before this registration

`tools/run_h6_date_arm.py` gained three things: tier `l5`, `--schema-version`
(default `v1`, so no banked invocation changes), and `--allow-busy-gpu` with the
same semantics as `run_ps_eval.py`'s. **The flag was NOT added to
`soak_load.py`, `latency_matrix.py`, `smoke_first_token.py` or
`bisect_hang.py`** - those exist to measure timing, and a bypass there would let
a contended number be reported as a clean one. Ten other copies of the guard
were left alone; this is deliberate and not an oversight.

The two gate cells, declared and unscored:

| item | outcome | class | what happened |
|---|---|---|---|
| `R03` | `correct` | `correct_with_tool` | called `add_business_days` with the delivery date, eight days and the full holiday list, and returned 24 March 2026 |
| `R11` | `off_by_calendar` | `result_ignored` | called `date_diff(2023-03-01, 2023-11-30)`, received **274**, and answered 274. The key is **275** because the pack's period is inclusive of both endpoints |

`R11` is worth stating plainly because it shapes what this experiment can find:
**the tool returns an exclusive day count and the question asks an inclusive
one, so the counting convention is not removed by the tool - it is relocated to
the boundary between the model and the tool.** Whether that generalises is what
the run measures.

### The arms

All four on the full 24-item L5 bank. **Band E is included as a control**: a
date tool has no business moving evidence work, and if it does, the effect is
the schema and not the arithmetic.

| arm | configuration |
|---|---|
| **A** | Qwen3-30B-A3B, `--tools off` - the control, re-run IN THIS HARNESS |
| **B** | Qwen3-30B-A3B, `--tools on --schema-version v2` |
| **C** | Qwen3-30B-A3B, `--tools preamble-only` - the preamble WITHOUT the tools field |
| **D** | Qwen3.8-27B `low`, `--tools on --schema-version v2` |

**Arm A is re-run rather than reused from E78.** This harness passes `--jinja`,
assembles the prompt differently and runs a multi-round loop. Comparing a
tool-harness arm against a `run_ps_eval` arm would attribute a harness
difference to the tool, which is Rule 8.

**Arm C is not optional.** E68 measured that merely OFFERING an irrelevant tool
cost this model **3 of 20** on a tier with no date questions in it, arriving as
non-termination rather than as wrong answers, and F94 records the tool schema as
a large, model-specific, non-monotonic variable. Without arm C a gain in B
cannot be separated from the prompt change that carries it.

### Predictions, each naming the FIELD it is scored against

| # | prediction | scored against |
|---|---|---|
| 1 | **cross-harness bridge:** the tool-free control reproduces E78 | arm A `band R correct` within 1 of E78's **3/12** |
| 2 | the model actually uses the tools | `n_calls >= 1` on at least **8 of 12** band-R items, arm B |
| 3 | the tool converts a material number of items | arm B `band R correct` minus arm A `band R correct` **>= 3** |
| 4 | **it does NOT close the gap.** Interest arithmetic and the inclusive/exclusive convention are not tool-addressable | arm B `band R correct` **<= 9 of 12**, against Qwen3.8's tool-free 11 |
| 5 | the preamble alone does not do it | arm C `band R correct` **<=** arm A `band R correct` + 1 |
| 6 | tools do not touch evidence work | absolute difference in `band E correct`, arm B against arm A, **<= 1** |
| 7 | **the cost is real and measurable here**, where E67's floor made it untestable | at least one item `correct` in arm A and not `correct` in arm B |
| 8 | E67's damage finding reproduces or is neutral | arm D `band R correct` **<= 11**, its tool-free E78 figure |

**Prediction 4 is the one that decides the routing question**, and it is
registered as a NEGATIVE. If it is falsified - if the tool takes the workhorse to
10 or more - that is a bigger result than any of the others and the routing guide
changes on the strength of it.

### Registered decision rule, tie-break included

| observed | action |
|---|---|
| P3 holds and arm B `band R` >= 10 with P7's regression count 0 | **the routing guide changes**: keep the workhorse resident with the V2 schema for counted-period work, and record the wall-time saving against Qwen3.8 |
| P3 holds and arm B `band R` is 6-9 | **partial**: the tool is worth having and does not replace the model swap. Record which MECHANISMS converted and which did not, because that list is the next experiment |
| P3 fails - arm B minus arm A < 3 | the tool does not generalise from E67's six date questions to a mixed reasoning band. Record it and do NOT extend the schema to chase it |
| P6 fails - band E moves by >= 2 | **the schema is acting on something other than arithmetic.** Treat the band-R gain as confounded and re-run with arm C as the baseline rather than arm A |
| **tie-break:** P3 holds AND P7 shows regressions >= the conversions | the tool is a wash. Report conversions and regressions separately and recommend nothing - a net-zero intervention that changes half the answers is worse than no intervention |
| any arm `transport_failed` > 1 | infrastructure, not capability. Re-run that arm before scoring anything |

## E79 RESULT - the tool helps the model that cannot reason and harms the model that can. The capability is knowing when NOT to call it. PREDICTION 6 FALSIFIED. (2026-08-28)

Four arms, 24 items, tier `l5`, `-c 16384`, `--jinja`, `-fa on`, `--max-rounds 6`,
kernel `7.0.0-29-generic`. **Rule 9 breached and acknowledged in every arm; all
wall times VOID and none is quoted.**

| arm | model | tools | total | **band R** | **band E** | band-R items calling | band-E items calling |
|---|---|---|---|---|---|---|---|
| **A** | Qwen3-30B-A3B | off | 13/24 | 3/12 | 10/12 | 0 | 0 |
| **B** | Qwen3-30B-A3B | **on, V2** | **11/24** | **6/12** | **5/12** | 12 | **10** |
| **C** | Qwen3-30B-A3B | preamble-only | 13/24 | 3/12 | 10/12 | 0 | 0 |
| **D** | Qwen3.8-27B `low` | **on, V2** | 22/24 | 10/12 | 12/12 | 12 | **0** |

### THE ANSWER

> **Both models use the tool well. Only one of them knows when not to.** On the
> band the tool is for, it called on 12 of 12 for both. On the band it is
> irrelevant to, **Qwen3.8 called on 0 of 12 and the workhorse called on 10 of
> 12** - and lost five items doing it. Same tools, same schema, same prompts,
> same bank.

Per model, each against its own tool-free baseline:

| model | band R tool-free -> tools | band E tool-free -> tools |
|---|---|---|
| Qwen3-30B-A3B | 3/12 -> **6/12** (+3, 0 regressions) | 10/12 -> **5/12** (+1, **-5** capability, -1 infrastructure) |
| Qwen3.8-27B | 11/12 -> **10/12** (0 conversions, **-1**) | 12/12 -> 12/12 (unchanged) |

**E67 reproduces exactly, in a new bank and a new schema version.** It found the
date tool *"rescues the weak model and damages the strong one"*. Here the weak
model gains three on the band the tool addresses, the strong model gains nothing
and loses one, and the strong model was already at 11/12 so there was nothing to
rescue.

### The mechanism, and `E02` is the whole of it

`E02` asks: *"What Liability Cap applies to the Site B (Ennis) work? Give the
amount in euro."* The workhorse, offered date tools, spent all six rounds on:

```
add_period({"date": "2026-02-16", "months": 6})            -> 2026-08-16
weekday({"date": "2026-08-16"})                            -> Sunday
roll_to_business_day({"date": "2026-08-16", ...})          -> 2026-08-17
add_business_days({"date": "2026-03-30", "days": 12, ...}) -> 2026-04-16
```

- date arithmetic, on a question about a liability cap - and never produced an
answer. All five capability regressions are that shape: `result_ignored` at
`n_calls = 6`, the round cap, no final content.

**This sharpens E68 rather than repeating it.** E68 established that offering an
irrelevant tool is not free and that the harm arrives as non-termination. E79
shows the mechanism: **the model does not ignore the tool, it tries to use it.**

### The cross-harness control is exact, which is what licenses everything above

Arm A is the workhorse with tools off, run in the TOOL harness. E78's
`l5-pilot-workhorse` is the same model and bank in `run_ps_eval`. **Zero of 24
per-item verdicts differ**, including the outcome distributions. So the two
harnesses agree completely with tools off, and arm D may be compared against
E78's tool-free Qwen3.8 despite the harness change. That comparison is still
one step weaker than a same-harness one, and no tool-free Qwen3.8 arm was run
here; it is stated rather than papered over.

### Scoring

| # | prediction | outcome |
|---|---|---|
| 1 | arm A `band R` within 1 of E78's 3/12 | **HELD exactly** - 3/12, and 0 of 24 verdicts differ |
| 2 | `n_calls >= 1` on >= 8 of 12 band-R items, arm B | **HELD** - 12 of 12 |
| 3 | arm B `band R` minus arm A >= 3 | **HELD at the threshold** - exactly 3 |
| 4 | arm B `band R` <= 9 of 12 | **HELD** - 6 |
| 5 | arm C `band R` <= arm A + 1 | **HELD** - 3 against 3 |
| 6 | band E moves by <= 1, arm B against arm A | **FALSIFIED** - it moved by **5** |
| 7 | at least one item correct in A and not in B | **HELD** - 6, of which 5 capability and 1 infrastructure |
| 8 | arm D `band R` <= 11 | **HELD** - 10, and against its own tool-free baseline it lost `R06` |

**Prediction 4 was registered as a negative and it held**, so the routing guide
does not change on the strength of a gap closed: the tool takes the workhorse to
6 of 12, against Qwen3.8's tool-free 11.

### Which mechanisms the tool converted, as the decision rule requires

| converted | not converted |
|---|---|
| `R03`, `R04`, `R05` - all three acceptance-window walks, each solved by one `add_business_days` call carrying the delivery date, the day count and the full holiday list | `R06` day count, `R07`/`R08` interest arithmetic, `R09` parallel periods, `R10` standstill suspension, `R11` inclusive/exclusive convention, `R12` composition |

**The tool converts exactly the mechanism it has a primitive for and nothing
else.** V2 added `add_business_days`; the three items it addresses converted and
the other nine did not. That is not a criticism of the tool - it is the shape of
what a tool can do, and it says the next primitive would buy at most the items
it directly implements.

`R11` is the one to keep. Both models called `date_diff(2023-03-01, 2023-11-30)`
and received a correct **274**. The workhorse answered 274; Qwen3.8 answered
**275**, because the pack's period is inclusive of both endpoints. **The tool did
not remove the counting convention, it relocated it to the boundary between the
model and the tool** - and bridging that boundary is the same capability the tool
was brought in to replace.

### The registered decision rule, and its TIE-BREAK, both fire

Two branches match, as registered:

- *"P3 holds and arm B band R is 6-9 -> partial: the tool is worth having and
  does not replace the model swap. Record which MECHANISMS converted."* Done
  above.
- *"P6 fails - band E moves by >= 2 -> treat the band-R gain as confounded and
  re-baseline on arm C."* Re-baselined. **Arms A and C are item-for-item
  identical**, so every figure above is unchanged by it. The preamble alone moved
  one band-R answer from `wrong` to `off_by_calendar` and changed no verdict.

And the tie-break, which is the one that decides:

> *"P3 holds AND P7 shows regressions >= the conversions -> the tool is a wash.
> Report conversions and regressions separately and recommend nothing - a
> net-zero intervention that changes half the answers is worse than no
> intervention."*

Conversions in arm B: **4** (3 band R, 1 band E). Capability regressions:
**5**. So the rule fires, and the measured outcome is worse than the wash it was
written for: **13/24 -> 11/24**.

**What ships: nothing, and specifically NOT an unconditional tool offer.** The
routing guide is not changed by this experiment.

### The recommendation this actually supports, stated separately from the rule

The tool is **+3 and -0 on band R** and **-5 on band E**. A system that offered
it only on counted-period questions would take the gain without the loss. That
system needs a classifier that decides when a question is about counting - which
is the discrimination Qwen3.8 demonstrated (0 of 12 spurious calls) and the
workhorse does not have (10 of 12).

So the plan's H8 and H19 - routing reasoning by task type - are not an
optimisation on top of the tools branch. **On this evidence they are a
precondition for it.** That is a different experiment and it needs its own
registration.

### Declared

- **One `transport_failed` in arm B** (`E09`, HTTP 500 from `llama-server`). The
  registered rule triggers a re-run above one, so it stands. It is counted as an
  infrastructure regression and never folded into the capability count;
  `tools/score_e79.py` separates them, and reporting all six band-E losses as
  capability would have overstated the effect by a fifth.
- **`--max-rounds 6` is a configuration and it bounds the harm.** Every capability
  regression sits exactly at the cap, so a larger cap might have let some finish
  - at a cost this experiment did not measure. The figure is 6 and the result is
  attributed to it.
- Arm D is the only arm on a model whose tool-free baseline comes from a
  different harness, per the control above.
